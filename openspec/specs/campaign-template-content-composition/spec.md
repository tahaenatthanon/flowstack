# campaign-template-content-composition Specification

## Purpose

กำหนดว่าแคมเปญอีเมลที่มาจาก template สำเร็จรูปแยก chrome (ดีไซน์ตายตัว — สี, ความกว้างการ์ด, padding, border, icon, รูปภาพ, โครงสร้าง) ออกจากเนื้อหาที่แก้ไขได้อย่างไร โดยใช้ editable-region marker ที่กำหนดเองทีละ template แทนการ auto-detect, จังหวะที่ประกอบ (compose) เป็น HTML เต็มก้อนแบบ deterministic, การจัดการ CTA เป็น field แยกจากตัวแก้ไขเนื้อหาหลัก, และการรองรับแคมเปญที่สร้างไว้ก่อนระบบนี้โดยไม่กระทบพฤติกรรมเดิม — เพื่อป้องกันปัญหาที่ `ArticleEditor` (TipTap) ทิ้ง HTML attribute ของ chrome ระหว่างแก้ไขเนื้อหา ซึ่งเคยทำให้ดีไซน์ของ template เสียหาย (เช่น ความกว้างการ์ด)

## Requirements

### Requirement: Template แต่ละตัวกำหนด editable-region marker เองด้วยมือ
`emailTemplates.ts` SHALL กำหนดตำแหน่งโซนเนื้อหาที่แก้ไขได้ของแต่ละ template ด้วย placeholder token `{{EMAIL_CONTENT}}` ที่ฝังไว้ในตำแหน่งที่เลือกเองทีละ template ไม่ใช้การตรวจจับอัตโนมัติ (auto-detect/regex หา `<p>`) — template ที่มีปุ่ม CTA ต้องกำหนด marker แยกเพิ่ม `{{CTA_TEXT}}` และ `{{CTA_URL}}`

#### Scenario: Template มี marker เนื้อหาครบ
- **WHEN** ตรวจสอบ field `html` ของ template ใดๆ ใน `emailTemplates.ts`
- **THEN** พบ token `{{EMAIL_CONTENT}}` ฝังอยู่ในตำแหน่งที่ถูกกำหนดไว้อย่างชัดเจนสำหรับ template นั้น

#### Scenario: Template ที่มี CTA มี marker CTA ครบ
- **WHEN** ตรวจสอบ template ที่มี `hasCta: true`
- **THEN** field `html` มี token `{{CTA_TEXT}}` และ `{{CTA_URL}}` ฝังอยู่ในตำแหน่งปุ่ม CTA ของ template นั้น

### Requirement: ตัวแก้ไขเนื้อหาเห็นเฉพาะโซนที่แก้ไขได้ ไม่เห็น chrome
เมื่อผู้ใช้เลือก template สำเร็จรูปในไดอะล็อกสร้าง/แก้ไขแคมเปญ ระบบ SHALL โหลดเฉพาะเนื้อหาเริ่มต้นของโซนแก้ไขได้ (`defaultContent`) เข้าตัวแก้ไข ไม่ใช่ HTML เต็มเอกสารของ template

#### Scenario: เลือก template แล้วตัวแก้ไขแสดงแค่เนื้อหา
- **WHEN** ผู้ใช้เลือก template จากแกลเลอรี
- **THEN** ตัวแก้ไข (`ArticleEditor`) แสดงเฉพาะเนื้อหาเริ่มต้นของโซนแก้ไขได้ ไม่แสดงหรือรับการแก้ไขส่วน chrome (สี, พื้นหลัง, ความกว้าง, ขอบ, icon, รูปภาพ, โครงสร้างตาราง) ใดๆ เลย

### Requirement: ประกอบ (compose) HTML เต็มก้อนแบบ deterministic จากเนื้อหาที่แก้ไขได้ + chrome ต้นฉบับ
ระบบ SHALL มีฟังก์ชัน compose ที่รับ template, เนื้อหาที่แก้ไขได้, และค่า CTA (ถ้ามี) แล้วคืนค่า HTML เต็มก้อนแบบ deterministic (input เดียวกันได้ output เดียวกันเสมอ) โดยแทนที่ `{{EMAIL_CONTENT}}` ด้วยเนื้อหาที่แก้ไข และแทนที่ `{{CTA_TEXT}}`/`{{CTA_URL}}` ด้วยค่า CTA ที่กำหนด — เรียกใช้ฟังก์ชันเดียวกันทั้งจากแท็บ "ตัวอย่าง" (ระหว่างแก้ไข ยังไม่บันทึก) และตอนบันทึกแคมเปญ

#### Scenario: ตัวอย่างตรงกับสิ่งที่จะถูกบันทึกเป๊ะ
- **WHEN** ผู้ใช้แก้ไขเนื้อหาแล้วเปิดแท็บ "ตัวอย่าง" โดยยังไม่ได้กดบันทึก
- **THEN** HTML ที่แสดงในแท็บ "ตัวอย่าง" ตรงกับ HTML ที่จะถูกบันทึกเป็น `body_html` เป๊ะทุกตัวอักษร หากกดบันทึกทันทีโดยไม่แก้ไขอะไรเพิ่ม

#### Scenario: Chrome เหมือนกัน 100% ระหว่างแก้ไขและไม่แก้ไข
- **WHEN** เปรียบเทียบอีเมลที่ส่งจากแคมเปญที่แก้ไขเนื้อหาแล้ว กับอีเมลจาก template เดียวกันที่ไม่ได้แก้ไขอะไร
- **THEN** ส่วน chrome (สี, พื้นหลัง, ความกว้างการ์ด, padding, border, icon, รูปภาพ, โครงสร้าง) เหมือนกันทุกจุดโดยไม่มีข้อยกเว้น ต่างกันเฉพาะข้อความในโซนที่แก้ไขได้เท่านั้น

### Requirement: CTA เป็น field โครงสร้างแยก ไม่ใช่ส่วนหนึ่งของเนื้อหาที่แก้ไขผ่าน rich-text editor
สำหรับ template ที่มี `hasCta: true` ระบบ SHALL แสดง field ข้อความปุ่มและ URL แยกต่างหากจากตัวแก้ไขเนื้อหาหลัก ผู้ใช้ SHALL NOT แก้ไขโครงสร้าง/สไตล์ของ CTA หลักของ template ผ่าน rich-text editor โดยตรง

#### Scenario: แก้ข้อความ/URL ของ CTA ผ่าน field แยก
- **WHEN** ผู้ใช้แก้ไขข้อความปุ่มหรือ URL ในช่อง CTA ที่แยกจากตัวแก้ไขเนื้อหาหลัก
- **THEN** HTML ที่ประกอบออกมามีข้อความ/URL ของปุ่ม CTA ตรงตามที่กำหนดในช่องนั้น โดยสไตล์/โครงสร้างปุ่ม (สี, border-radius) ไม่เปลี่ยนแปลง

#### Scenario: ปุ่มเสริมที่แทรกเองในเนื้อหายังใช้งานได้ตามปกติ
- **WHEN** ผู้ใช้ใช้ปุ่ม "แทรกปุ่มลิงก์ในอีเมล" ในแถบเครื่องมือของตัวแก้ไข เพื่อแทรกลิงก์/ปุ่มเสริมเองภายในโซนเนื้อหาที่แก้ไขได้
- **THEN** ปุ่มเสริมนั้นถูกแทรกและแสดงผลตามปกติ ไม่ถูกจำกัดหรือแยกออกจากเนื้อหาที่แก้ไขได้ (คนละกลไกกับ CTA หลักของ template)

### Requirement: จัดเก็บเนื้อหาดิบแยกจาก HTML ที่ประกอบแล้ว เพื่อรองรับการเปิดแก้ไขซ้ำ
ระบบ SHALL บันทึกเนื้อหาที่แก้ไขได้ดิบ (`editable_content`) และค่า CTA ดิบ (`cta_text`, `cta_url`) แยกจาก `body_html` ที่ประกอบแล้ว เพื่อให้เปิดแก้ไขแคมเปญร่างซ้ำได้โดยโหลดค่าดิบกลับเข้าตัวแก้ไขโดยตรง ไม่ต้องแกะออกจาก `body_html` ที่ประกอบแล้ว

#### Scenario: เปิดแก้ไขแคมเปญร่างที่สร้างด้วยระบบใหม่ซ้ำ
- **WHEN** ผู้ใช้เปิด "แก้ไข" แคมเปญร่างที่มี `editable_content` ไม่เป็นค่าว่าง (สร้างด้วยระบบ chrome-lock ใหม่)
- **THEN** ตัวแก้ไขโหลดเนื้อหาจาก `editable_content` และช่อง CTA (ถ้ามี) โหลดจาก `cta_text`/`cta_url` กลับมาให้แก้ไขต่อได้ถูกต้อง ไม่มีการแกะเนื้อหาจาก `body_html`

### Requirement: แคมเปญที่สร้างก่อนระบบนี้ (ไม่มีเนื้อหาดิบ) ยังคงแก้ไขผ่านช่องทางเดิมได้
เมื่อ `editable_content` ของแคมเปญเป็นค่าว่าง (แคมเปญที่สร้างก่อน migration นี้) ระบบ SHALL เปิดไดอะล็อกแก้ไขในโหมดเดิม (โหลด `body_html` ทั้งก้อนเข้าตัวแก้ไขโดยตรง ไม่ผ่านกลไก compose/chrome-lock ใหม่)

#### Scenario: เปิดแก้ไขแคมเปญร่างเก่าที่สร้างก่อน migration
- **WHEN** ผู้ใช้เปิด "แก้ไข" แคมเปญร่างที่มี `editable_content` เป็นค่าว่าง
- **THEN** ตัวแก้ไขโหลด `body_html` ทั้งก้อนเข้ามาให้แก้ไขได้อิสระเหมือนพฤติกรรมก่อนการเปลี่ยนแปลงนี้ทุกประการ (รวมถึงความเสี่ยงเดิมที่ chrome อาจเปลี่ยนแปลงถ้าถูกแก้ไข)

### Requirement: Backend ไม่ประกอบ design ใหม่จาก template ตอนส่งอีเมล
เมื่อส่งแคมเปญอีเมลที่ผ่านการ compose ด้วยระบบนี้ ระบบ SHALL ใช้ `body_html` ที่บันทึกไว้ตรงๆ ทำเฉพาะการแทนที่ merge tags และแทรก tracking pixel/wrap link เท่านั้น ไม่ดึง template ปัจจุบันมาประกอบ chrome ใหม่ ณ เวลาส่ง

#### Scenario: ส่งแคมเปญที่ผ่านการ compose แล้ว
- **WHEN** ระบบส่งแคมเปญที่มี `body_html` ถูกประกอบไว้แล้วตั้งแต่ตอนบันทึก
- **THEN** อีเมลที่ส่งถึงผู้รับมีเนื้อหา chrome ตรงกับตอนบันทึกทุกประการ แม้ template ต้นฉบับใน `emailTemplates.ts` จะถูกแก้ไขในโค้ดหลังจากนั้นก็ตาม

### Requirement: การเปลี่ยนแปลงนี้ไม่กระทบ ArticleEditor หรือหน้าเนื้อหาบทความ
กลไก chrome-lock/marker composition นี้ SHALL จำกัดอยู่เฉพาะฝั่งแคมเปญอีเมล (`CampaignsPage.tsx`) เท่านั้น SHALL NOT เปลี่ยนแปลง behavior ของ `ArticleEditor.tsx` แบบ global หรือกระทบหน้าเนื้อหาบทความ (`ContentCardDialog.tsx`)

#### Scenario: หน้าเนื้อหาบทความทำงานเหมือนเดิมทุกประการ
- **WHEN** ผู้ใช้แก้ไขเนื้อหาบทความในหน้าเนื้อหา (ไม่ใช่แคมเปญอีเมล)
- **THEN** พฤติกรรมการแก้ไข/บันทึกเป็นไปตามปกติเหมือนก่อนการเปลี่ยนแปลงนี้ ไม่มีแนวคิด chrome/editable-zone เข้ามาเกี่ยวข้อง

### Requirement: แคมเปญที่ไม่ได้มาจาก template ไม่ได้รับผลกระทบ
แคมเปญที่สร้างโดยไม่ได้เลือก template สำเร็จรูป (`template_id` เป็นค่าว่าง) SHALL ยังคงแก้ไขผ่านตัวแก้ไขแบบทั้งเอกสารเหมือนพฤติกรรมปัจจุบันทุกประการ ไม่มีแนวคิดโซนแก้ไขได้/chrome มาเกี่ยวข้อง

#### Scenario: สร้างแคมเปญแบบเขียนเองยังทำงานเหมือนเดิม
- **WHEN** ผู้ใช้สร้างแคมเปญโดยไม่เลือก template ใดๆ แล้วพิมพ์เนื้อหาเองทั้งหมด
- **THEN** ตัวแก้ไขให้แก้ไขได้อิสระทั้งเอกสารเหมือนพฤติกรรมปัจจุบัน ไม่มีข้อจำกัดเพิ่มเติมจากการเปลี่ยนแปลงนี้

### Requirement: CTA ที่ปลายทางล็อกตายตัว (mailto) แก้ได้เฉพาะข้อความปุ่ม
เมื่อปุ่ม CTA ของ template ปลายทางเป็น `mailto:{{company_email}}` (ที่อยู่ผูกกับข้อมูลบริษัท ไม่ใช่ URL ที่ควรกำหนดต่อแคมเปญ) ระบบ SHALL ไม่แสดง field ให้แก้ URL ของ CTA — ผู้ใช้แก้ได้เฉพาะข้อความปุ่มผ่าน `{{CTA_TEXT}}` เท่านั้น ปลายทาง `mailto:{{company_email}}` เป็นส่วนหนึ่งของ chrome ที่ล็อกตายตัว

#### Scenario: เลือก template ที่มี CTA แบบ mailto
- **WHEN** ผู้ใช้เลือก template ที่ปุ่ม CTA ปลายทางเป็น `mailto:{{company_email}}`
- **THEN** ไดอะล็อกแคมเปญแสดงเฉพาะ field ข้อความปุ่มให้แก้ ไม่แสดง field URL

#### Scenario: บันทึกแคมเปญที่ใช้ template CTA แบบ mailto
- **WHEN** ผู้ใช้แก้ข้อความปุ่มแล้วบันทึกแคมเปญที่ใช้ template ประเภทนี้
- **THEN** HTML ที่ประกอบออกมามีปุ่มที่ข้อความตรงตามที่แก้ไข แต่ href ยังคงเป็น `mailto:{{company_email}}` เหมือนเดิมทุกครั้ง ไม่ว่าจะแก้ข้อความปุ่มเป็นอะไรก็ตาม

### Requirement: Template รองรับ dynamic content field เฉพาะทางนอกเหนือจาก EMAIL_CONTENT และ CTA
สำหรับ template ที่มีค่าตัวเลข/ข้อความสั้นที่ต้องเปลี่ยนทุกครั้งที่ใช้งาน (เช่น เปอร์เซ็นต์ส่วนลด, เวลานับถอยหลัง) แต่ไม่ใช่เนื้อหาอิสระแบบ EMAIL_CONTENT และไม่ใช่ CTA ระบบ SHALL รองรับ field เฉพาะทางที่กำหนดชื่อ marker เองต่อ template (ไม่ใช่กลไกทั่วไปที่กำหนด field ได้อิสระ) โดยแสดง input แยกต่างหากให้ผู้ใช้กรอกค่า และคงโครงสร้าง/สี/ขนาด/ตำแหน่งของส่วนนั้นเป็น chrome ล็อกตายตัว

#### Scenario: เลือก template ที่มี dynamic field เฉพาะทาง
- **WHEN** ผู้ใช้เลือก template ที่รองรับ dynamic field เฉพาะทาง (เช่น ส่วนลดและเวลานับถอยหลัง)
- **THEN** ไดอะล็อกแคมเปญแสดง input แยกสำหรับแต่ละ field พร้อมค่าเริ่มต้นจาก template

#### Scenario: บันทึกแคมเปญที่แก้ค่า dynamic field
- **WHEN** ผู้ใช้แก้ค่าใน dynamic field แล้วบันทึกแคมเปญ
- **THEN** HTML ที่ประกอบออกมามีค่าที่แก้ไขแสดงในตำแหน่งเดิมของ chrome โดยโครงสร้าง สี ขนาด และตำแหน่งของส่วนนั้นไม่เปลี่ยนแปลง
