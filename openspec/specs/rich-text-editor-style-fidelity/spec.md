# rich-text-editor-style-fidelity Specification

## Purpose

ควบคุมว่า `ArticleEditor` (TipTap-based, ใช้ร่วมกันทั้งในไดอะล็อกแคมเปญอีเมลและไดอะล็อกเนื้อหาบทความ) เก็บรักษา inline styling และ structural element ใดบ้างไว้ เมื่อ parse HTML เข้ามาครั้งแรกและ re-serialize กลับเป็น HTML ทุกครั้งที่ผู้ใช้แก้ไขเนื้อหา — โดยไม่ขึ้นกับว่าหน้าไหนเป็นคนเรียกใช้ editor แยกจาก `email-campaign-template-picker` ซึ่งดูแลพฤติกรรมของแท็บตัวอย่าง (preview) ในไดอะล็อกสร้างแคมเปญ

## Requirements

### Requirement: ตัวแก้ไขต้องคงสไตล์ของตาราง (table/tr/td/th) ไว้หลังแก้ไขเนื้อหา
`ArticleEditor` SHALL คง `style` attribute แบบ inline ที่ผูกอยู่กับ `<table>`, `<tr>`, `<td>`, `<th>` ไว้ครบถ้วน ทั้งตอน parse เนื้อหาเข้ามาครั้งแรกและตอน re-serialize กลับเป็น HTML ทุกครั้งที่ผู้ใช้แก้ไขเนื้อหา

#### Scenario: แก้ข้อความในตารางที่มีสีพื้นหลัง แล้วสีไม่หาย
- **WHEN** ผู้ใช้พิมพ์แก้ไขข้อความในส่วนที่อยู่ภายใน `<td>` ที่มี `style="background-color:..."`
- **THEN** เนื้อหา HTML ที่ได้จากตัวแก้ไข (`editor.getHTML()`) ยังคงมี `style="background-color:..."` บน `<td>` นั้นอยู่ครบ ไม่ถูกตัดทิ้ง

#### Scenario: แก้ข้อความในส่วนอื่นของเอกสาร ตารางที่ไม่ได้แก้ก็ยังคงสไตล์ไว้
- **WHEN** ผู้ใช้แก้ไขข้อความในส่วนหนึ่งของเนื้อหา ขณะที่มีตารางอื่นที่มี inline style อยู่ในเอกสารเดียวกันแต่ไม่ได้ถูกแก้ไข
- **THEN** ตารางที่ไม่ได้ถูกแก้ไขยังคง `style` attribute เดิมไว้ครบถ้วนเช่นกัน

### Requirement: ตัวแก้ไขต้องคงสไตล์ของหัวข้อ (h1-h4) ไว้หลังแก้ไขเนื้อหา
`ArticleEditor` SHALL คง `style` attribute แบบ inline ที่ผูกอยู่กับ heading ระดับ 1 ถึง 4 (`<h1>`-`<h4>`) ไว้ครบถ้วน ทั้งตอน parse เนื้อหาเข้ามาครั้งแรกและตอน re-serialize กลับเป็น HTML ทุกครั้งที่ผู้ใช้แก้ไขเนื้อหา

#### Scenario: แก้ข้อความในหัวข้อที่กำหนดสีตัวอักษรไว้ แล้วสีไม่หาย
- **WHEN** ผู้ใช้พิมพ์แก้ไขข้อความภายใน `<h1>` (หรือ h2-h4) ที่มี `style="color:..."`
- **THEN** เนื้อหา HTML ที่ได้จากตัวแก้ไขยังคงมี `style="color:..."` บน heading นั้นอยู่ครบ ไม่ถูกตัดทิ้ง

### Requirement: ตัวแก้ไขต้องรองรับ `<div>` พร้อมสไตล์ของมันไว้หลังแก้ไขเนื้อหา
`ArticleEditor` SHALL รองรับ element `<div>` เป็น block node ในเนื้อหาที่แก้ไขได้ พร้อมคง `style` attribute แบบ inline ของมันไว้ ทั้งตอน parse เนื้อหาเข้ามาครั้งแรกและตอน re-serialize กลับเป็น HTML ทุกครั้งที่ผู้ใช้แก้ไขเนื้อหา — ไม่ว่า `<div>` นั้นจะห่อข้อความธรรมดาหรือห่อ element ระดับ block เช่น `<p>` ไว้ข้างในก็ตาม

#### Scenario: แก้ข้อความในเนื้อหาที่มี div ตกแต่งอยู่ แล้ว div ไม่หายไป
- **WHEN** เนื้อหาที่โหลดเข้าตัวแก้ไขมี `<div style="display:flex;...">` ที่ห่อข้อความ/สัญลักษณ์ธรรมดาไว้ข้างใน (เช่น วงกลมไอคอนตกแต่งของ template หรูหราสีม่วง) และผู้ใช้แก้ไขข้อความส่วนอื่นในเอกสารเดียวกัน
- **THEN** เนื้อหา HTML ที่ได้จากตัวแก้ไขยังคงมี `<div style="display:flex;...">` อยู่ครบ ไม่ถูกตัดทิ้งหรือ unwrap กลายเป็นข้อความเปล่า

#### Scenario: แก้ข้อความในเนื้อหาที่มี div ห่อ paragraph ไว้ข้างใน แล้วโครงสร้างไม่กระจัดกระจาย
- **WHEN** เนื้อหาที่โหลดเข้าตัวแก้ไขมี `<div style="border:...">` ที่ห่อ `<p>` หนึ่งอันหรือมากกว่าไว้ข้างใน (เช่น กล่องข้อความเน้นของ template หรูหรูระดับพรีเมียม) และผู้ใช้แก้ไขข้อความส่วนอื่นในเอกสารเดียวกัน
- **THEN** เนื้อหา HTML ที่ได้จากตัวแก้ไขยังคงมี `<p>` ทั้งหมดอยู่ภายใน `<div>` เดิมตามโครงสร้างเดิม ไม่ถูกดีดออกมาเป็น sibling ของ `<div>` และ `<div>` ไม่กลายเป็นกล่องว่างเปล่า

### Requirement: ตัวแก้ไขต้องคงสไตล์ของรายการ (bulletList/listItem) ไว้หลังแก้ไขเนื้อหา
`ArticleEditor` SHALL คง `style` attribute แบบ inline ที่ผูกอยู่กับ `<ul>` (bulletList) และ `<li>` (listItem) ไว้ครบถ้วน ทั้งตอน parse เนื้อหาเข้ามาครั้งแรกและตอน re-serialize กลับเป็น HTML ทุกครั้งที่ผู้ใช้แก้ไขเนื้อหา

#### Scenario: แก้ข้อความในรายการที่มีสีกำหนดไว้ แล้วสีไม่หาย
- **WHEN** ผู้ใช้พิมพ์แก้ไขข้อความภายใน `<li>` ที่มี `style="color:..."` หรือ `<ul>` ที่มี `style` กำหนดไว้
- **THEN** เนื้อหา HTML ที่ได้จากตัวแก้ไข (`editor.getHTML()`) ยังคงมี `style` attribute บน `<ul>`/`<li>` นั้นอยู่ครบ ไม่ถูกตัดทิ้ง

#### Scenario: แก้ไขเนื้อหาที่มาจากการประกอบแบบโครงสร้าง (heading/blocks) ไม่เสียสไตล์ list
- **WHEN** ผู้ใช้เปิดแก้ไขแคมเปญที่เนื้อหาส่วน list ถูกประกอบมาจาก AI generation (แปลง `blocks[]` ประเภท `list` เป็น `<ul>`/`<li>` ที่มี inline style ตามสีของ template)
- **THEN** หลังแก้ไขข้อความส่วนอื่นแล้วบันทึก สไตล์ของ `<ul>`/`<li>` ยังคงตรงกับที่ประกอบไว้ตอน generate ไม่ถูกรีเซ็ตเป็นค่าเริ่มต้นของ browser

### Requirement: การเพิ่มการรองรับ style ต้องไม่กระทบเนื้อหาบทความเดิมที่ไม่มีสไตล์เหล่านี้
เนื่องจาก `ArticleEditor` ถูกใช้ร่วมกันทั้งในไดอะล็อกแคมเปญอีเมลและไดอะล็อกเนื้อหาบทความ การเพิ่มการรองรับ `style`/`<div>` ตาม requirement ข้างต้น SHALL ไม่เปลี่ยนแปลงพฤติกรรมของเนื้อหาบทความที่ไม่มี inline style หรือ `<div>` เหล่านี้อยู่แล้ว

#### Scenario: บทความปกติที่ไม่มี inline style ยังทำงานเหมือนเดิม
- **WHEN** ผู้ใช้แก้ไขเนื้อหาบทความทั่วไปในไดอะล็อกเนื้อหา (ไม่มี `<table>`/`<div>` ที่มี inline style)
- **THEN** พฤติกรรมการแก้ไข/บันทึกเนื้อหาเป็นไปตามปกติเหมือนก่อนการเปลี่ยนแปลงนี้ ไม่มีผลข้างเคียงที่สังเกตเห็นได้
