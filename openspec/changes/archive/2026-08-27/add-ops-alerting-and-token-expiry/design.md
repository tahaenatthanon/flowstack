## Context

ระบบมีเส้นทางความล้มเหลวครบแล้ว แต่ไม่มีเส้นทางบอกคน — `publish-scheduler.php` เขียน `status='failed'` แล้วจบ, `content-metrics-sync.php` นับ `errors` ใส่ `cron_runs` แล้วจบ, `api/health.php` มีอยู่แต่ไม่มีอะไรเรียก หลักฐานที่นับได้จากฐานข้อมูลจริง: `content_publish_queue` มีแถว `failed` 60 แถวย้อนไปถึง 14 มิ.ย. · Facebook token หมดอายุ 3 ครั้ง (21, 24, 26 ส.ค. 2026) · `content-metrics-sync` ล้ม 4 รอบติด · คืน 24 ส.ค. ตัวตั้งเวลาไม่เรียก `tick.php` เลย 15 ชั่วโมง ทุกเรื่องถูกพบด้วยการเปิดฐานข้อมูลดู

ข้อจำกัดที่กำหนดรูปทรงของงานนี้:

- **ไฟล์งาน cron ถูก `include` เข้าโปรเซสเดียวกัน** (`type='include'` — `publish-scheduler`, `content-metrics-sync`, `ai-digest`) ชื่อ global ที่ซ้ำทำให้ PHP fatal `Cannot redeclare` ซึ่ง try/catch ดักไม่ได้และฆ่า tick ทั้งรอบ ไฟล์เดิมจึงตั้งชื่อเลี่ยงกันไว้แล้ว (`isCancelled` / `metricsSyncCancelled`)
- **`cron-runner.php` อ่านผลจาก stdout ด้วย `preg_match`** (`/(\d+)\s+entries/i`, `/(\d+)\s+error/i`) ที่นับ match แรก และ `cron_runs.notes` เก็บ 500 ตัวอักษรแรก ข้อความที่พิมพ์ก่อนบรรทัดสรุปจึงเปลี่ยนตัวเลขในฐานข้อมูลได้
- **นาฬิกา:** เส้นทาง cron ห้ามใช้ `time()`/`date()` ของ PHP ตัดสินเวลา ต้องเอา "เดี๋ยวนี้" จากฐานข้อมูล
- **สิทธิ์แอดมินอยู่ที่ `tenant_users.is_admin`** ไม่ใช่ `users.is_admin` และ `users` ไม่มีคอลัมน์ `tenant_id` เลย
- **มี 4 tenant** ในระบบ; แอดมินของ tenant อื่นต้องไม่ได้รับแจ้งเตือนของ `tenant-default`
- **ช่องทางส่งที่ใช้ได้จริง:** in-app (`ai_notifications` 31 แถว มี badge ใน `ChatWidget`), email (PHPMailer/SMTP2GO ตั้งค่าครบ), LINE (token ครบแต่ปลายทางเป็นกลุ่มที่ยังไม่ยืนยันว่าเป็นกลุ่มภายใน), Telegram (bot token ว่าง — ใช้ไม่ได้)
- **`content-metrics-sync` รันทุก 6 ชั่วโมง** (`0 */6 * * *`) ส่วน `publish-scheduler` รันทุกนาที (`* * * * *`)

## Goals / Non-Goals

**Goals:**

- ความล้มเหลวที่เกิดขึ้นแล้วต้องมีคนรู้ภายในเวลาที่แก้ได้ทัน โดยไม่ต้องมีใครเปิดฐานข้อมูลดู
- credentials ที่จะหมดอายุต้องรู้ล่วงหน้าก่อนที่การเผยแพร่จะพัง ไม่ใช่รู้ตอนพังแล้ว
- ตัวแจ้งเตือนต้องไม่กลายเป็นจุดล้มใหม่ — งานที่กำลังจัดการความล้มเหลวต้องทำงานต่อได้แม้ตัวแจ้งเตือนล้มพร้อมกัน
- ไม่มีใครต้องตั้งค่าอะไรเพิ่มเพื่อให้แจ้งเตือนพื้นฐานทำงาน
- ปิดช่องทางที่พิสูจน์แล้วว่าส่งไม่ได้ เพื่อไม่ให้มีคนตั้งเวลาโพสต์ไปที่ที่ไม่มีทางสำเร็จ

**Non-Goals:**

- **ไม่แก้สาเหตุของความล้มเหลว** — Instagram creds ว่าง, TikTok ไม่ส่ง `video_url`, LinkedIn ส่ง path ในเครื่อง, `views` ที่เป็น 0 ถาวรเพราะ Meta ยกเลิก metric — งานนี้ทำให้ปัญหามองเห็น ไม่ใช่แก้ปัญหา
- **ไม่ตั้งระบบเฝ้าระวังภายนอก** — `api/health.php` จะพร้อมให้เรียก แต่การตั้ง uptime monitor ให้เรียกอยู่นอกขอบเขต (ต้องทำที่ระดับโครงสร้างพื้นฐาน ไม่ใช่ในโค้ด)
- **ไม่แตะ `notification_settings` และ `notification-dispatch.php`** — นั่นคือ briefing รายบุคคลตาม `briefing_time` คนละเรื่องกับการแจ้งความล้มเหลวระดับระบบ
- **ไม่ส่ง LINE/Telegram จริงในรอบนี้**
- **ไม่ทำหน้าจอรวมศูนย์ดู alert ย้อนหลัง** — `ops_alerts` และ `notification_log` เก็บข้อมูลไว้ให้ query ได้ แต่ไม่มี UI ในรอบนี้

## Decisions

### 1. ส่งเข้าแอปทุกกรณี + อีเมลเฉพาะเรื่องด่วน

in-app คือช่องทางเดียวที่ไม่มีต้นทุนตั้งค่าและมี UI รออยู่แล้ว (`ai-notifications.php` + badge ใน `ChatWidget.tsx`) จึงเป็นพื้น อีเมลเติมเฉพาะเรื่องที่รอให้คนเปิดเว็บไม่ได้

*ทางเลือกที่ไม่เอา:* **อีเมลทุกกรณี** — 60 แถวที่ล้มเหลวสะสมแปลว่าจะมีอีเมลจำนวนมากในช่วงแรก และคนจะตั้ง filter ทิ้ง · **in-app เท่านั้น** — ปิดกรณี "token หมดอายุตอนไม่มีใครเปิดเว็บ" ไม่ได้ · **LINE เป็นหลัก** — ถอนข้อความคืนไม่ได้ และแจ้งเตือนมีเนื้อ error ดิบจาก Graph API (ชื่อเพจ, token id) ปลายทางที่มีอยู่ (`line_targets` → กลุ่ม `Cf75763e…`) ยังไม่ยืนยันว่าเป็นกลุ่มภายใน

LINE ยังเดินสายไว้แต่อ่านปลายทางจาก key ใหม่ `ops_alert_line_targets` ที่ตั้งเป็นค่าว่าง — เปิดใช้ทีหลังได้โดยไม่แก้โค้ด และไม่ใช้ `line_targets` เดิมเพื่อไม่ให้เผลอส่งไปกลุ่มลูกค้า

### 2. ใช้ `ai_notifications.type='custom'` ไม่เพิ่มค่า enum

`type` เป็น ENUM(`overdue`,`deadline`,`daily_digest`,`revenue`,`custom`) — `custom` ครอบได้อยู่แล้ว การ ALTER enum บนตารางที่ใช้งานจริงเพื่อเพิ่มค่าที่ไม่มีใครแยกแยะในโค้ดคือความเสี่ยงที่ไม่ได้อะไรกลับมา ถ้าวันหน้าต้องกรองเฉพาะ ops alert ให้กรองจาก `ops_alerts` ที่มี `alert_key` แทน

### 3. คีย์แจ้งเตือนผูกกับ "เรื่อง" ไม่ใช่ "เหตุการณ์" + เพดาน 1 ครั้ง/ชั่วโมง

`publish-scheduler` รันทุกนาที ความล้มเหลวหนึ่งเรื่องเกิดซ้ำได้ 60 ครั้ง/ชั่วโมง ถ้าแจ้งทุกครั้งผู้รับจะปิดการแจ้งเตือนเองภายในวันเดียว `alert_key` จึงเป็นเรื่อง (`publish_fail:facebook`) ไม่ใช่ id ของแถวคิว และมีตาราง `ops_alerts` เก็บ `last_sent_at` ไว้เทียบ

`resolved_at` + ข้อความ "กลับมาปกติ" จำเป็นคู่กัน เพราะเมื่อมีเพดาน ความเงียบจะแปลได้สองอย่าง — หายแล้ว หรือถูกกลืน ถ้าไม่มีข้อความปิดเรื่อง เพดานจะกลายเป็นการซ่อนปัญหา

*ทางเลือกที่ไม่เอา:* **เพดานแบบ exponential backoff** — เดาพฤติกรรมล่วงหน้าโดยไม่มีข้อมูลว่าคนอยากถูกเตือนบ่อยแค่ไหน เพิ่มความซับซ้อนที่ทดสอบยาก · **สรุปรวมส่งวันละครั้ง** — token หมดอายุรอถึงพรุ่งนี้ไม่ได้

### 4. แจ้งเตือน cron อยู่ใน `runJob()` ไม่ใช่ใน `tick.php`

`runJob()` เป็นจุดเดียวที่ทั้งปุ่มของแอดมินและตัวตั้งเวลาผ่าน และเป็นที่ที่ `$success`/`$errors` ถูกคำนวณอยู่แล้ว วางที่นี่ได้ครอบทั้ง 7 งานด้วยโค้ดชุดเดียวและครอบทั้งสองทางเรียก ถ้าวางใน `tick.php` งานที่แอดมินกดรันมือจะล้มโดยไม่แจ้งใคร และจะเกิดตรรกะตัดสิน "ล้มเหลว" สองชุดที่เพี้ยนออกจากกันได้ — ซึ่งเป็นเรื่องเดียวกับที่ spec `cron-job-dispatch` มีข้อกำหนดให้ตัวรันงานอยู่ไฟล์เดียวอยู่แล้ว

งานที่ค้างเกินเพดานแล้วถูกปิด (`notes = 'Force-restarted after timeout'`) นับเป็นความล้มเหลวด้วย เพราะงานที่แขวนค้างรุนแรงกว่างานที่ล้มแล้วจบ

### 5. ผู้รับ = แอดมินของ tenant ที่เกี่ยวข้อง จาก `tenant_users`

`requireAdmin()` ตัดสินจาก `tenant_users.is_admin` การใช้ `users.is_admin` จะให้จำนวนเท่ากันโดยบังเอิญแต่ผิดที่มา และจะรวมแอดมินของ tenant อื่นเข้ามาด้วย (มี 2 คน) จึง join `tenant_users tu` กับ `users u` แล้วกรอง `tu.is_admin=1 AND u.is_active=1 AND tu.tenant_id = <tenant ของทรัพยากร>` เขียนหนึ่งแถว `ai_notifications` ต่อแอดมิน โดยใส่ `tenant_id` ของแอดมินคนนั้นเอง — เพราะ `ai-notifications.php` อ่านแบบ `WHERE tenant_id = ? AND user_id = ?` แถวที่ใส่ tenant ผิดจะมองไม่เห็น

**ไม่ join `notification_settings`** — แอดมิน 4 จาก 5 คนไม่มีแถวในตารางนั้น การอิงตารางนี้จะทำให้แจ้งเตือนถึงคนเดียวโดยดูเหมือนทำงานปกติ ซึ่งแย่กว่าไม่มีแจ้งเตือนเลย

### 6. tenant ของ alert ระดับ cron หามาจากข้อมูล ไม่ฝังค่า

`runJob()` ไม่มี tenant ให้อ้าง (งานรันข้าม tenant) ผู้รับจึงหาจาก tenant ที่มีช่องทางเผยแพร่ `is_active=1` อย่างน้อยหนึ่งช่องทาง ปัจจุบันได้ `tenant-default` เท่านั้น ซึ่งตรงกับที่ต้องการ แต่ยังถูกต้องเองถ้ามี tenant ใหม่เริ่มใช้งานจริง การฝัง `'tenant-default'` ไว้ในโค้ดจะให้ผลเหมือนกันวันนี้แล้วเงียบผิดวันหน้า

### 7. การตรวจอายุ token อาศัย `content-metrics-sync` ไม่สร้าง cron ใหม่

งานนี้รันทุก 6 ชั่วโมงและถอดรหัส creds ของช่องทางอยู่แล้ว การเพิ่มงาน cron ใหม่หมายถึงแถวใหม่ใน `cron_jobs` + ไฟล์ใหม่ + จุดล้มใหม่ เพื่อทำสิ่งที่งานเดิมทำได้ในบรรทัดแรก ที่ 6 ชั่วโมง/รอบ และช่องทาง facebook/instagram ที่ตรวจได้ไม่กี่ช่องทาง ปริมาณเรียก Graph API อยู่ระดับไม่ถึง 10 ครั้ง/วัน

**ต้องวางไว้ก่อนบรรทัดที่ query แถวคิว** เพราะไฟล์ `return` ออกกลางทางเมื่อไม่มีโพสต์ให้ซิงก์ — และ "ไม่มีโพสต์ให้ซิงก์" คือสถานะที่พบบ่อยที่สุดตอน token หมดอายุ (ไม่มีอะไรเผยแพร่สำเร็จให้ซิงก์) ถ้าวางหลังจุดนั้น การตรวจจะไม่ทำงานในรอบที่ต้องการมันที่สุด

**ผลการตรวจต้องพิมพ์หลังบรรทัดสรุปในทั้งสองทางออก** ไม่งั้น `preg_match` ของ `cron-runner.php` จะอ่านตัวเลขจากส่วนตรวจ token ไปใส่ `cron_runs.records_processed`/`errors` และบรรทัดสรุปจะหลุดออกจาก 500 ตัวอักษรของ `notes`

### 8. `expires_at = 0` เก็บเป็น NULL และแยก `data_access_expires_at` เป็นเดดไลน์ของตัวเอง

Graph API ใช้ `0` แทน "ไม่มีวันหมดอายุ" ซึ่งเป็นค่าที่ Page token ของระบบคืนอยู่ การเก็บตรง ๆ จะทำให้ทุกช่องทางดูเหมือนหมดอายุมาแล้ว 56 ปี

`data_access_expires_at` เป็นหน้าต่างคนละตัว — token ที่ไม่มีวันหมดอายุยังหยุดเข้าถึงข้อมูลได้เมื่อพ้นหน้าต่างนี้ ของช่องทาง Facebook ปัจจุบันคือ **24 พ.ย. 2026** ซึ่งเป็นเดดไลน์จริงที่ใกล้ที่สุดของทั้งระบบ ถ้าเก็บแต่ `token_expires_at` หน้าจอจะรายงานว่า "ไม่มีวันหมดอายุ" แล้ววันนั้นทุกอย่างพังพร้อมกัน

`token_status='unsupported'` สำหรับ 8 ช่องทางที่ไม่ใช่ facebook/instagram — ต้องแยกจาก `valid` เพราะการแสดงว่าปกติคือการรับประกันสิ่งที่ระบบไม่ได้ตรวจ และต้องไม่นับเป็น error ของรอบรัน

### 9. ตัวแจ้งเตือนต้องล้มเงียบได้ และตั้งชื่อด้วยคำนำหน้า `ops_`

ทุกจุดเรียกอยู่ในเส้นทางที่กำลังจัดการความล้มเหลวอยู่แล้ว ถ้าตัวแจ้งเตือนโยน exception มันจะกลบข้อมูลความล้มเหลวต้นทางและอาจฆ่ารอบ tick ทั้งรอบ ตัวมันเองจึงห่อ try/catch ทั้งก้อนและรายงานผ่าน `error_log()` เท่านั้น

ฟังก์ชันและค่าคงที่ทั้งหมดใน `api/lib/ops-alert.php` ใช้คำนำหน้า `ops_` ตามธรรมเนียมที่ `cron-runner.php` บันทึกไว้ — include-mode ทำให้ชื่อ global ชนกันได้ และ `Cannot redeclare` ดักด้วย try/catch ไม่ได้

ข้อความแจ้งเตือนต้องไม่มีตัวเลขติดกับคำ `error`/`entries` ด้วยเหตุผลเดียวกับข้อ 7

### 10. ปิด 3 ช่องทางด้วยข้อมูล ไม่ใช่ด้วยโค้ด

`UPDATE publish_channels SET is_active=0` สำหรับ `instagram`, `tiktok`, `linkedin` — `publish-scheduler.php:31` กรอง `pc.is_active = 1` อยู่แล้ว การปิดจึงกัน cron ได้จริงโดยไม่ต้องลบเส้นทางโค้ด และเมื่อแก้บั๊ก dispatch ของช่องทางนั้นเสร็จก็เปิดกลับด้วย UPDATE เดียวโดยไม่ต้อง revert commit

`twitter` และ `wix` **ไม่แตะ** — ไม่มีหลักฐานทั้งทางบวกและทางลบ (0 แถวในคิว, ไม่พบบั๊กชัดในโค้ด) การปิดโดยไม่มีหลักฐานคือการเดา

### 11. ที่อยู่ของข้อกำหนดใน spec

ข้อกำหนดเรื่อง "การเผยแพร่ล้มเหลวถาวรต้องแจ้งเตือน" อยู่ใน spec `ops-failure-alerting` ไม่ใช่ `content-publish-result-tracking` — spec หลังกำหนดว่า**อะไรถูกบันทึก**ลงฐานข้อมูล ซึ่งไม่เปลี่ยนเลยใน change นี้ ส่วน "ใครได้รู้" เป็นเรื่องใหม่ทั้งเรื่อง กลับกัน `cron-job-dispatch` และ `post-metrics-sync` ได้ delta เพราะ spec ทั้งสองระบุหน้าที่ของตัวรันงานไว้เป็นรายการปิด ถ้าไม่อัปเดตจะเหลือรายการที่ไม่ครบและอ่านผิดได้

## Risks / Trade-offs

**[`tick.php` ไม่ถูกเรียกเลย → ไม่มี alert ใดทำงาน]** → เป็นข้อจำกัดที่ปิดจากในระบบไม่ได้ เพราะ alert ทุกตัวอยู่ในเส้นทาง cron `api/health.php` จะรายงานงานที่เลยกำหนดให้ระบบภายนอกเรียกตรวจ แต่**ต้องมีคนตั้ง uptime monitor ให้เรียก** งานนี้จะไม่ถือว่าปิดช่องว่างนี้สำเร็จจนกว่าจะมีตัวเรียกจริง

**[แจ้งเตือนล้นจนคนเลิกอ่าน]** → เพดาน 1 ครั้ง/ชั่วโมง/เรื่อง + คีย์ระดับเรื่องไม่ใช่ระดับแถว + อีเมลเฉพาะเรื่องด่วนและเฉพาะเมื่อล้มติดกัน 3 รอบ + ข้อความปิดเรื่องเมื่อกลับมาปกติ

**[in-app เห็นได้เฉพาะเมื่อเปิดเว็บ]** → ยอมรับ และชดเชยด้วยอีเมลสำหรับเรื่องด่วน (token/สิทธิ์) ซึ่งเป็นชุดเรื่องที่รอไม่ได้จริง

**[SMTP ล่มทำให้อีเมลหายเงียบ]** → `notification_log` บันทึกความล้มเหลวของแต่ละช่องทาง และ in-app ถูกส่งทุกกรณีอยู่แล้ว การล้มของอีเมลจึงไม่เท่ากับไม่มีใครได้รับ

**[แจ้งเตือนมีเนื้อ error ดิบ (ชื่อเพจ, token id, URL) ปนอยู่]** → in-app เห็นได้เฉพาะแอดมินของ tenant นั้น, ข้อความถูกตัดความยาว, และ LINE ปิดโดยค่าเริ่มต้นเพราะข้อความ LINE ถอนคืนไม่ได้

**[ตัวแจ้งเตือนเขียนฐานข้อมูลเพิ่มในเส้นทาง cron ที่รันทุกนาที]** → เขียนเฉพาะเมื่อมีความล้มเหลว และเพดานทำให้จำนวนการเขียนสูงสุดคือ 1 ครั้ง/ชั่วโมง/เรื่อง ในรอบปกติที่ไม่มีอะไรล้มจะมี query เพิ่มเป็นการอ่าน `ops_alerts` เพื่อปิดเรื่องที่ค้าง

**[ถ้ามีคนเปลี่ยน `content-metrics-sync` ให้รันถี่ขึ้น การตรวจ token จะยิง Graph API ถี่ตาม]** → ที่ `0 */6 * * *` คือไม่ถึง 10 ครั้ง/วัน ยอมรับได้ ถ้าวันหน้าเปลี่ยนเป็นทุกนาทีจะต้องเพิ่มการหรี่ด้วย `token_checked_at` — บันทึกไว้เป็นเงื่อนไข ไม่ทำล่วงหน้าในรอบนี้

**[ปิด 3 ช่องทางแล้วมีคนตั้งเวลาโพสต์ไว้ล่วงหน้า]** → แถวคิวที่ค้างอยู่จะไม่ถูกหยิบเพราะ `pc.is_active=1` กรองออก และจะไม่ถูกลบทิ้ง (คงไว้เป็นหลักฐาน) — ผู้ใช้ที่ตั้งไว้จะไม่ได้รับการเผยแพร่และจะไม่มีแจ้งเตือน เพราะช่องทางไม่เข้าเส้นทาง dispatch เลย นี่คือพฤติกรรมเดิมของการปิดช่องทาง ไม่ใช่สิ่งที่ change นี้ทำให้แย่ลง

## Migration Plan

3 migration แยกไฟล์ ตามลำดับ:

1. `ops_alerts` — ตารางใหม่ ไม่กระทบข้อมูลเดิม
2. คอลัมน์อายุ token ใน `publish_channels` — เพิ่มคอลัมน์ NULL ทั้งหมด แถวเดิม 10 แถวได้ `token_status = NULL` (= ยังไม่เคยตรวจ) ไม่มีข้อมูลเดิมถูกแก้
3. `UPDATE publish_channels SET is_active=0 WHERE platform IN ('instagram','tiktok','linkedin')` + settings key `ops_alert_line_targets` เป็นค่าว่าง

ทุกไฟล์รันด้วย `/c/xampp/mysql/bin/mysql.exe -u root flowstack < <file>` แล้วยืนยันด้วย `SHOW COLUMNS` / `SELECT` ทันทีตามกฎของโครงการ

**Rollback:** `DROP TABLE ops_alerts` · `ALTER TABLE publish_channels DROP COLUMN` ทั้ง 5 คอลัมน์ · `UPDATE publish_channels SET is_active=1 WHERE platform IN ('instagram','tiktok','linkedin')` — ไม่มี migration ใดลบหรือเขียนทับข้อมูลเดิม จึงย้อนได้ครบโดยไม่ต้องกู้ข้อมูล

**ลำดับการ deploy:** migration ทั้ง 3 → `api/lib/ops-alert.php` → จุดเรียกทั้ง 4 จุด → `health.php` → UI → `scripts/test-ops-alert.php` เพื่อพิสูจน์เส้นทางส่งก่อนรอให้ระบบล้มเอง

## Open Questions

- **ใครตั้ง uptime monitor ให้เรียก `api/health.php` และเรียกจากที่ไหน** — จำเป็นต่อการปิดช่องว่าง "cron ไม่ถูกเรียกเลย" แต่เป็นงานระดับโครงสร้างพื้นฐาน ต้องตัดสินแยกจาก change นี้
- **กลุ่ม LINE `Cf75763e…` เป็นกลุ่มภายในหรือมีลูกค้าอยู่ด้วย** — ถ้ายืนยันว่าภายใน จะเติมลง `ops_alert_line_targets` ได้ทันทีโดยไม่แก้โค้ด
- **เกณฑ์ 7 วันก่อนหมดอายุเหมาะไหม** — เลือกจากสมมติฐานว่าการต่ออายุ Facebook token ใช้เวลาไม่เกินหนึ่งสัปดาห์ ถ้าจริง ๆ ต้องประสานงานนานกว่านั้นควรขยับเป็น 14 วัน (แก้ค่าคงที่จุดเดียว)
