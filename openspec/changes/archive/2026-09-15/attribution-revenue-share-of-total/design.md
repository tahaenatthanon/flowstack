## Context

หลัง archive change `localize-campaign-attribution-ui` ไปแล้ว ได้คุยกับผู้ร้องขอเรื่องความหมายของคอลัมน์ "สัดส่วน" ในตาราง `SourceTable` (แท็บ Attribution) และพบว่าสูตรปัจจุบัน (% เทียบแหล่งที่มาที่มีรายได้สูงสุด) ตอบคำถามคนละแบบกับที่ต้องการจริง — ผู้ร้องขอต้องการเห็น "แหล่งนี้คิดเป็นกี่ % ของรายได้รวมทั้งหมด" ไม่ใช่ "แหล่งนี้ใกล้เคียงอันดับหนึ่งแค่ไหน" การเปลี่ยนแปลงนี้แก้เฉพาะฐานการคำนวณ ไม่แตะโครงสร้างตารางหรือ backend

## Goals / Non-Goals

**Goals:**
- คอลัมน์ "สัดส่วน" แสดง % ที่คำนวณจาก `won_value` ของแถวนั้น หารด้วยผลรวม `won_value` ของทุกแถวในตาราง — ตัวเลขทุกแถวรวมกัน ≈ 100%
- ความกว้างของแท่งภาพอิงฐานเดียวกับตัวเลข % (ยืนยันกับผู้ร้องขอแล้วผ่าน AskUserQuestion) — แท่งกับตัวเลขไม่ขัดแย้งกันเอง
- กรณีทุกแถวมี `won_value = 0` ต้องไม่เกิด `NaN` หรือหารด้วยศูนย์ — แสดง "0%" ทุกแถว

**Non-Goals:**
- ไม่เปลี่ยนหัวคอลัมน์ "สัดส่วน" (คำนี้ยังใช้ได้กับทั้งสองความหมาย)
- ไม่เปลี่ยน `CampaignTable` หรือคอลัมน์อื่นในหน้าเดียวกัน — จุดนี้กระทบเฉพาะคอลัมน์สัดส่วนใน `SourceTable`
- ไม่เปลี่ยน backend/API — คำนวณฝั่ง client จากข้อมูลที่มีอยู่แล้วในทุก response
- ไม่เปลี่ยนสี/ลำดับแถว/การเรียงตาราง (เรียงตาม `won_value DESC` จาก backend อยู่แล้ว ไม่เกี่ยวกับการเปลี่ยนนี้)

## Decisions

**Decision 1 — เปลี่ยนฐานทั้งตัวเลขและความกว้างแท่งพร้อมกัน (ไม่ใช่แค่ตัวเลข)**
ทางเลือกที่พิจารณา: คงความกว้างแท่งไว้แบบเดิม (เทียบอันดับหนึ่ง เพื่อให้เห็นการเปรียบเทียบชัดด้วยสายตา) แล้วเปลี่ยนแค่ตัวเลขกำกับเป็นแบบสัดส่วนรวม — ตัดออกเพราะจะทำให้แท่งกับตัวเลขสื่อความหมายขัดกันเอง (เช่น แถวอันดับหนึ่งแท่งเต็มคอลัมน์แต่ตัวเลขโชว์ "88%" ไม่ใช่ "100%" ทำให้ผู้ใช้สับสนว่าทำไมแท่งเต็มแต่ตัวเลขไม่ใช่ 100) ผู้ร้องขอยืนยันให้เปลี่ยนทั้งคู่พร้อมกันแล้ว

**Decision 2 — สูตรใหม่: `pct = total > 0 ? (won_value / total * 100) : 0`**
```js
// เดิม
const maxValue = Math.max(...rows.map(r => r.won_value), 1);
const barPct = Math.min(100, r.won_value / maxValue * 100);

// ใหม่
const total = rows.reduce((sum, r) => sum + r.won_value, 0) || 1;  // กัน division by zero แบบเดียวกับของเดิม
const barPct = Math.min(100, r.won_value / total * 100);
```
ใช้ `|| 1` (ไม่ใช่ `Math.max(total, 1)`) เพราะ `total` มาจาก `reduce` เริ่มที่ 0 และไม่มีทางติดลบ (`won_value` เป็นเงิน ไม่ติดลบ) — `|| 1` จึงพอเพียงและอ่านง่ายกว่า ผลลัพธ์เหมือนกันทุกกรณี: ถ้า `total = 0` (ทุกแถว `won_value = 0`) จะได้ `0/1*100 = 0` ทุกแถว ไม่มี `NaN`

**Decision 3 — ไม่ต้อง cap ที่ 100% อีกต่อไปในทางทฤษฎี แต่คง `Math.min(100, ...)` ไว้เผื่อความปลอดภัย**
ในทางคณิตศาสตร์ `won_value / total` ของแต่ละแถวจะไม่มีทางเกิน 100% เมื่อทุก `won_value` เป็นบวกหรือศูนย์ (ผลรวมของส่วนย่อยที่ไม่ติดลบ ย่อมไม่เกินผลรวมทั้งหมด) แต่คง `Math.min(100, ...)` ไว้เป็น defensive code เดิม เผื่อกรณีข้อมูลผิดปกติ (เช่น floating-point rounding เกิน 100.00001%) — ไม่มีความเสี่ยงเพิ่มจากการคงไว้

## Risks / Trade-offs

- **[Risk] ผู้ใช้ที่คุ้นกับพฤติกรรมเดิม (แหล่งอันดับหนึ่ง = แท่งเต็มคอลัมน์เสมอ) จะเห็นแท่งอันดับหนึ่งสั้นลง** โดยเฉพาะเมื่อมีหลายแหล่งที่มาใกล้เคียงกัน (ไม่มีแหล่งไหนครองสัดส่วนเด่นชัด) → **Mitigation:** เป็นการเปลี่ยนแปลงที่ตั้งใจและยืนยันแล้ว ความหมายใหม่ (ส่วนแบ่งจากรายได้รวม) มีประโยชน์เชิงวิเคราะห์มากกว่าความหมายเดิม (อันดับเทียบกัน)
- **[Risk] ตัวเลขรวมอาจไม่ตรง 100% เป๊ะเพราะการปัดเศษ** (เช่น 33% + 33% + 33% = 99%) → **Mitigation:** แก้ด้วยการแสดงทศนิยม 1 ตำแหน่ง (`barPct.toFixed(1)`) แทนการปัดเศษเป็นจำนวนเต็ม (`Math.round`) ตามคำขอเพิ่มเติมหลัง apply รอบแรก — จากข้อมูลจริงที่ตรวจ ผลรวมแม่นยำถึง 100.0% พอดี ลดความคลาดเคลื่อนจากการปัดเศษได้มาก
- **[Risk] Regression ต่อ test ที่มีอยู่** → ตรวจแล้วไม่มี test ใน `src/__tests__/` อ้างอิง `AttributionTab`, `barPct`, `SourceTable`, หรือคำว่า "สัดส่วน" จึงไม่คาดว่าจะพัง

## Migration Plan

1. แก้สูตรใน `SourceTable` (`AttributionTab.tsx`) จุดเดียว — ทั้งตัวเลขและความกว้างแท่งใช้ตัวแปร `total` เดียวกัน
2. ไม่ต้องใช้ feature flag — เป็นการแก้สูตรคำนวณในรีลีสเดียว ไม่มี DB migration ไม่มี API change
3. Rollback: revert commit ที่เกี่ยวข้อง ไม่มีข้อมูลถูกทำลาย
