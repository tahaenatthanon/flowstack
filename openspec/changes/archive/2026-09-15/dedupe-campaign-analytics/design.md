## Context

`/marketing` (`MarketingPage.tsx`) เป็นหน้าจัดการแคมเปญอีเมลแบบมีแท็บ: แคมเปญ (รายการ + ส่ง), Templates, กลุ่มลูกค้า, ลูกค้า, รายงาน (analytics), Attribution แท็บ "รายงาน" คำนวณค่าต่างๆ เองฝั่ง client จากผล `useEmailCampaigns()` ที่โหลดมาทั้งหมดโดยไม่กรอง — ผลรวมส่ง/เปิด/คลิก, อัตราเปิด/คลิกเฉลี่ย, อันดับ "แคมเปญที่ดีที่สุด" (top 3 เรียงตาม **อัตรา**เปิด) และตารางประสิทธิภาพเต็ม

`/campaign-analytics` (`CampaignAnalyticsPage.tsx`) เป็นหน้าแยกต่างหาก เข้าถึงได้จากเมนูข้าง มีข้อมูลจาก `GET /api/campaign-analytics.php?range=30d|90d|12m` คำนวณข้อมูลชุดเดียวกันฝั่ง server แต่กรองตามช่วงเวลาที่เลือกได้ พร้อมกราฟแนวโน้ม, กราฟสัดส่วนสถานะ และอันดับ top-5 (เรียงตาม**จำนวน**เปิดดิบ ไม่ใช่อัตรา)

`docs/features.md` ระบุไว้ว่า `/marketing` (§20 "สร้าง & ส่งอีเมล") มีหน้าที่แค่สร้าง/ส่งแคมเปญเท่านั้น ส่วน `/campaign-analytics` (§33) เป็นเจ้าของ scope "ภาพรวมทุกแคมเปญ... กราฟเปรียบเทียบ... Top performing campaigns... กรองตามช่วงวันที่" แต่เพียงผู้เดียว แท็บ "รายงาน" ถูกเพิ่มเข้ามาทีหลังโดยไม่มีการอัปเดตเอกสาร และตอนนี้ทำหน้าที่ซ้ำกับ §33 ด้วยตรรกะการคำนวณที่ต่างกัน (all-time เทียบกับกรองช่วงเวลา, เรียงตามอัตราเทียบกับเรียงตามจำนวนดิบ) — ทำให้ทั้งสองหน้าแสดงตัวเลข "เดียวกันในนาม" ไม่ตรงกันได้อย่างถูกต้องตามตรรกะของแต่ละฝั่ง

อีกจุดที่แยกออกมา: แท็บ "แคมเปญ" บน `/marketing` เองก็มีการ์ดสรุป all-time ของตัวเองอยู่แล้ว (แคมเปญทั้งหมด, ส่งทั้งหมด, เปิดอ่าน, คลิกทั้งหมด) มาจากข้อมูล `useEmailCampaigns()` ชุดเดียวกับที่แท็บ "รายงาน" เคยใช้ — ดังนั้นการตัดแท็บ "รายงาน" ออกไม่ได้ทำให้หน้านี้เสีย "จุดดูข้อมูลเร็วๆ" ไป เพราะมีอยู่แล้วในแท็บแรกที่ผู้ใช้เห็นตอนเปิดหน้ามา

## Goals / Non-Goals

**Goals:**
- ทั้งระบบมีที่เดียวเท่านั้นที่คำนวณและแสดง analytics ประสิทธิภาพแคมเปญ: `/campaign-analytics`
- ที่นั่นที่เดียว กรองทุก query ที่ผูกกับช่วงเวลา (สรุปสถิติ, แคมเปญยอดนิยม) ด้วยวันที่ **ส่งจริง** ไม่ใช่วันที่ **สร้าง** — ให้ตรงกับกราฟแนวโน้มที่ทำถูกอยู่แล้ว
- การ์ดสรุป all-time ที่มีอยู่แล้วบนแท็บ "แคมเปญ" ของ `/marketing` ไม่ถูกแตะต้อง — เป็นคนละเรื่องกัน (ภาพรวม pipeline ไม่ใช่รายงานตามช่วงเวลา) ที่มีเอกสารรองรับอยู่แล้ว จึงไม่อยู่ใน scope ของงานนี้
- แก้ลิงก์ข้ามหน้าที่ค้างอยู่จุดเดียว (`/campaign-analytics` ยังมี breadcrumb เขียน "การตลาด" ชี้ไป `/marketing` ที่เปลี่ยนชื่อเป็น "แคมเปญอีเมล" ไปแล้วในงานก่อนหน้า) ให้ตรงกัน

**Non-Goals:**
- ไม่เปลี่ยนสิ่งที่ `/campaign-analytics` แสดงหรือหน้าตา (ไม่มีกราฟใหม่ ไม่มีตัวกรองใหม่) — งานนี้แค่ตัดของซ้ำออก ไม่ได้ออกแบบหน้าที่เหลือใหม่
- ไม่แตะการ์ดสรุป all-time ของแท็บ "แคมเปญ" แม้ว่าในทางทฤษฎีจะเลขไม่ตรงกับ `/campaign-analytics` ที่กรองช่วงเวลาได้เหมือนกัน — เป็นเรื่องที่แยกกันและมีเอกสารรองรับอยู่แล้ว (ดูเหตุผลใน Context) การรื้อเรื่องนี้ใหม่ไม่อยู่ใน scope
- ไม่แก้ปัญหาอื่นที่เจอระหว่างสำรวจซึ่งเป็นต้นเหตุของงานนี้ (label ภาษาอังกฤษหลุด, หัวตารางผิด, TS type `CustomerStats` ที่ผิด, merge tag `{{subject}}` ที่ใช้ไม่ได้, ไฟล์ตาย `CampaignsPage.tsx`, entry ซ้ำใน `GlobalSearch`) — เป็นคนละเรื่อง แยก track ไว้ ไม่รวมเข้างานนี้

## Decisions

**Decision 1 — ตัดแท็บ "รายงาน" ออกทั้งหมด แทนที่จะย่อให้เหลือแค่การ์ดสรุป + ปุ่มลิงก์**
ทางเลือกที่พิจารณา:
- *(i) เก็บแท็บไว้ เปลี่ยนแหล่งข้อมูลไปใช้ `campaign-analytics.php` แต่คง UI ตาราง/top-3 เต็มไว้* — ตัดออก เพราะยังต้อง maintain UI สองชุดที่แสดงข้อมูลชุดเดียวกัน และไม่ได้ลดความสับสน "จะเชื่อตัวเลขไหน" เพียงแค่ทำให้ตัวเลขทั้งสองที่เท่ากัน แต่ก็ยังแสดงซ้ำสองที่อยู่ดี
- *(ii) เก็บแท็บไว้แบบย่อ เหลือแค่การ์ดสรุป + ปุ่ม "ดูรายงานเต็ม" ลิงก์ไป `/campaign-analytics`* — ตัดออกหลังพิจารณาละเอียด เพราะคุณค่า "ดูเร็วๆ โดยไม่ต้องออกจากหน้า" ที่ทางนี้ต้องการรักษาไว้นั้น มีอยู่แล้วในการ์ดสรุปของแท็บ "แคมเปญ" (แท็บแรกที่ผู้ใช้เห็น) การมีแท็บที่สองที่เหลือแค่ปุ่มลิงก์ ไม่ต่างจากไม่มีแท็บนั้นเลยอย่างมีนัยสำคัญ แต่ยังต้อง maintain TabsTrigger/TabsContent และเสียความสนใจผู้ใช้ในการตัดสินใจว่าจะกดดูไหม
- *(iv, เลือกใช้) ตัดแท็บออกทั้งหมด* — `/campaign-analytics` เข้าถึงได้จากเมนูข้างอยู่แล้วในคลิกเดียว ("วิเคราะห์แคมเปญ" ไม่ได้ซ่อนอยู่ใต้ `/marketing`) จึงไม่เสียการเข้าถึง และยังเป็นการทำให้โค้ดกลับไปตรงกับ scope ที่ `docs/features.md` ระบุไว้ตั้งแต่ก่อนที่แท็บนี้จะถูกเพิ่มเข้ามา ไม่ใช่การสร้าง scope ใหม่

**Decision 2 — แก้ตัวกรองช่วงเวลาให้ใช้ `sent_at` และยอมรับว่าแคมเปญสถานะ `sending` ที่ `sent_at` ยังเป็น NULL จะหายไปจากผลลัพธ์ที่กรองตามช่วงเวลาจนกว่าจะส่งเสร็จ**
ทางเลือกที่พิจารณา: ใช้ `COALESCE(sent_at, created_at) >= cutoff` เพื่อให้แคมเปญที่กำลังส่งอยู่ยังคงแสดงทันที — ตัดออก เพราะระหว่างสถานะ `sending` ค่า `total_opens`/`total_clicks` ของแคมเปญนั้นยังไม่ครบ (ยังส่งไม่จบ) การรวมเข้าไปในสรุป "ประสิทธิภาพช่วง 30 วัน" จะทำให้เห็นตัวเลขที่ยังไม่สมบูรณ์และกระโดดอีกทีตอนส่งเสร็จ การตัดออกจนกว่า `sent_at` จะถูกตั้งค่า ง่ายกว่าและไม่ทำให้เห็นตัวเลขที่ดูเหมือนพังชั่วคราว ส่วนตาราง "แคมเปญทั้งหมด" ที่ไม่กรองช่วงเวลาใน `campaign-analytics.php` ไม่ได้รับผลกระทบ ยังคงแสดงแคมเปญที่กำลังส่งอยู่ตามปกติ

**Decision 3 — ไม่รวมปัญหาอีก 8 ข้อที่เจอระหว่างสำรวจเข้ามาในงานนี้**
เป็นเรื่องที่แยกกัน ความเสี่ยงต่ำกว่า (ส่วนใหญ่เป็นการแก้ข้อความ/label) หรือมี scope ของตัวเองอยู่แล้ว (TS type ที่ผิด, merge tag ที่ใช้ไม่ได้, ไฟล์ตาย) การรวมเข้ามาจะทำให้งานนี้รีวิว/ย้อนกลับยากขึ้นในฐานะหน่วยเดียว หากต้องการทำสามารถเสนอเป็น change แยกได้ภายหลังตามลำดับความสำคัญ

## Risks / Trade-offs

- **[Risk] ผู้ใช้ที่เคยพึ่งพาแท็บ "รายงาน" แบบ *all-time* จะเสียมุมมองนั้นไป** (`/campaign-analytics` default มาที่มุมมองแบบกรองช่วงเวลา เช่น 30 วัน) → **Mitigation:** ตัวเลือกช่วงเวลาของ `/campaign-analytics` มี "12 เดือนล่าสุด" เป็นช่วงกว้างสุดอยู่แล้ว ส่วนตัวเลขรวมแบบ all-time จริงๆ ยังดูได้จากการ์ดสรุปของแท็บ "แคมเปญ" บน `/marketing` (ไม่กรองช่วงเวลา ตามดีไซน์เดิม)
- **[Risk] ลบ state ของแท็บที่อาจมีโค้ดส่วนอื่นอ่านอยู่** — `sentCampaigns`, `totalOpens`, `totalClicks`, `avgOpenRate`, `avgClickRate`, `bestCampaigns` ใน `MarketingPage.tsx` ตอนนี้ประกาศไว้ระดับ component ไม่ได้อยู่ใน JSX ของแท็บโดยตรง ต้องเช็คให้แน่ใจว่าไม่มีแท็บอื่น (แคมเปญ, ลูกค้า) อ่านค่าพวกนี้ก่อนลบ → **Mitigation:** grep หาการใช้งานของแต่ละตัวแปรทั่วทั้งไฟล์ก่อนลบ (กำหนดเป็น task แยกไว้ชัดเจน)
- **[Risk] การเปลี่ยน `created_at` → `sent_at` ทำให้ตัวเลขย้อนหลังที่ผู้ใช้เคยเห็นเปลี่ยนไป** (เช่น screenshot รายเดือนที่แคปไว้ก่อนแก้ จะไม่สามารถ reproduce ตัวเลขเดิมได้อีกหลังแก้) → **Mitigation:** นี่คือการแก้ให้ถูกต้องตามที่ตั้งใจ (ตัวเลขเดิมผิด) ไม่ใช่ regression ไม่ต้อง migrate ข้อมูลเพราะเป็นการกรองตอน query ไม่ใช่ข้อมูลที่เก็บไว้

## Migration Plan

1. แก้ filter ใน `api/campaign-analytics.php` ก่อน (เป็นการแก้ backend ที่ additive/แก้ให้ถูก ปล่อยแยกได้ทันทีและตรวจสอบผลได้ทันทีผ่าน `GET /api/campaign-analytics.php?range=30d`)
2. ตัดแท็บ "รายงาน" และ state ที่ตายแล้วออกจาก `MarketingPage.tsx`
3. แก้ label ของ breadcrumb ใน `CampaignAnalyticsPage.tsx`
4. ไม่ต้องใช้ feature flag — เป็นการตัด UI + แก้ query ให้ถูกต้องในรีลีสเดียว ไม่ใช่การทยอยเปิดใช้ ไม่มี DB migration
5. Rollback: revert commit ที่เกี่ยวข้อง ไม่มีข้อมูลถูก migrate หรือถูกทำลาย
