## Context

มีจุด render ตัวอย่างอีเมลด้วย `<iframe>` อยู่ 3 จุดใน `CampaignsPage.tsx` แต่หลังจาก change ก่อนหน้า (`fix-campaign-preview-template-double-wrap`, archive แล้ว) เนื้อหาที่เป็น template เต็ม (`<html>...`) จะ bypass ฟังก์ชัน `buildEmailPreviewHtml()` ไปเลย ทำให้เหลือแค่ 2 จุดที่ยังมีความเสี่ยงเรื่องความกว้าง:

1. **ไดอะล็อก "ดู" ของแท็บเทมเพลตหลัก** — `srcDoc={tpl.html}` ตรงๆ ไม่ผ่าน `buildEmailPreviewHtml()` แต่ dialog กว้างแค่ `sm:max-w-3xl` (768px) ซึ่งยังโดน cap เพิ่มด้วย `sm:max-w-[calc(100vw-2rem)]` จาก base Dialog primitive (`src/components/ui/dialog.tsx`) เมื่อวิวพอร์ตแคบกว่า ~800px กรอบ preview จริงจะแคบกว่า 600px และ container ใช้ `overflow-auto` (เลื่อนได้ แต่ scrollbar เล็กจนสังเกตยาก)
2. **แท็บ "ตัวอย่าง" ในไดอะล็อกสร้าง/แก้ไขแคมเปญ** — เนื้อหาที่ไม่ใช่ template เต็ม (พิมพ์เอง หรือดึงจาก AI/บทความ) ยังคงผ่าน `buildEmailPreviewHtml()` ซึ่งครอบด้วย div "การ์ด" (`max-width:600px;...;overflow:hidden`) — ถ้าเนื้อหาข้างในมีองค์ประกอบที่กว้างเกิน 600px แบบตายตัว (เช่น ตารางที่แทรกผ่านปุ่ม "ตาราง" ใน `ArticleEditor`) ส่วนเกินจะถูก `overflow:hidden` ตัดทิ้งแบบไม่มี scrollbar ให้เลื่อนเลย — มองไม่เห็นถาวร ต่างจากจุดที่ 1 ที่อย่างน้อยยังเลื่อนดูได้

จุดที่ 2 คือบั๊กที่แท้จริง (เนื้อหาหายถาวร ไม่ใช่แค่ UX ไม่สะดวก) ส่วนจุดที่ 1 เป็นปัญหาด้าน UX/sizing มากกว่า (เลื่อนได้แต่สังเกตยาก)

## Goals / Non-Goals

**Goals:**
- เนื้อหาที่กว้างเกินกรอบ preview ต้อง**เลื่อนดูได้เสมอ** ไม่ว่าจะผ่านจุดไหน — ห้ามมีกรณีที่เนื้อหาถูกตัดทิ้งแบบไม่มีทางเห็นได้อีกเลย (แก้ที่จุดที่ 2 โดยตรง)
- ลดความถี่ที่ผู้ใช้ต้องเลื่อนดูตั้งแต่แรกบนหน้าจอเดสก์ท็อปทั่วไป โดยขยายกรอบไดอะล็อก "ดู" template ให้กว้างขึ้น

**Non-Goals:**
- ไม่ทำ responsive scaling/ย่อเนื้อหา 600px ให้พอดีจอแคบมากๆ (เช่น มือถือ) — บนจอที่แคบจริงๆ ยอมรับว่ายังต้องเลื่อนแนวนอนดู (ตรงกับพฤติกรรมของ email client จริง)
- ไม่แก้โครงสร้างข้อมูล template หรือวิธีเก็บเนื้อหาใน `campaignBody`
- ไม่รับประกันว่าจะไม่ต้องเลื่อนดูเลย 100% ในทุกความกว้างวิวพอร์ต (ยังมี viewport แคบมากที่ยังต้องเลื่อนอยู่ดี) — เป้าหมายคือ "ลดความถี่" ไม่ใช่ "กำจัดให้หมด"

## Decisions

### Decision 1: เปลี่ยน `overflow:hidden` เป็น `overflow-x:auto` ในการ์ดของ `buildEmailPreviewHtml()`
แก้ inline style ของ div การ์ด (`max-width:600px;margin:0 auto;background:#fff;border-radius:8px;overflow:hidden;...`) เปลี่ยน `overflow:hidden` เป็น `overflow-x:auto` — นี่คือ correctness fix ตรงจุด แก้ปัญหาเนื้อหาหายถาวรจากตารางกว้างหรือองค์ประกอบอื่นที่มีความกว้างตายตัวเกิน 600px

**ทางเลือกที่พิจารณาแล้วไม่เลือก:**
- *ใช้ `overflow:auto` (ทั้งแนวตั้งและแนวนอน)* — การ์ดสูงตามเนื้อหาอยู่แล้ว (ไม่มี `max-height` กำกับ) ไม่มีเหตุผลต้อง scroll แนวตั้งซ้อนกับ scroll ของ iframe เอง การใช้ `overflow-x:auto` เจาะจงเฉพาะแนวนอนที่มีปัญหาจริงชัดเจนกว่า
- *จำกัดความกว้างตารางที่แทรกได้ในตัวแก้ไข (เช่น บังคับ max-width:100% ที่ระดับ Tiptap Table extension)* — เปลี่ยน behavior ของตัวแก้ไขเอง กระทบ use case อื่นที่อาจตั้งใจสร้างตารางกว้าง (เช่น export ไป PDF) เกินขอบเขตของบั๊กนี้ที่เกี่ยวกับ "preview" เท่านั้น จึงเลือกแก้ที่ preview layer แทน

### Decision 2: ขยายความกว้างไดอะล็อก "ดู" ของแท็บเทมเพลตหลักจาก `sm:max-w-3xl` เป็น `sm:max-w-4xl`
เพิ่มจาก 768px เป็น 896px — ลดวิวพอร์ตขั้นต่ำที่จะเริ่มโดน cap จาก `sm:max-w-[calc(100vw-2rem)]` (จาก ~800px ลงมาเหลือ ~928px แต่ในทางกลับกันหมายความว่าที่วิวพอร์ต 800-928px จะได้ประโยชน์เพิ่มจากคลาสนี้) กรอบ preview จริง (หลังหักส่วนขอบ/padding ~50px) จะกว้างพอสำหรับ 600px โดยไม่ต้องเลื่อนบนวิวพอร์ตเดสก์ท็อปทั่วไป (≥1024px ซึ่งเป็นเรื่องปกติอยู่แล้ว) และช่วยเพิ่มเติมในช่วงวิวพอร์ตกลางๆ ด้วย

**ทางเลือกที่พิจารณาแล้วไม่เลือก:**
- *ขยายเป็น fixed pixel width ที่คำนวณแม่นยำ (เช่น `sm:max-w-[680px]`)* — เปราะบางกว่า ผูกกับตัวเลข padding/border ปัจจุบันที่อาจเปลี่ยนได้ในอนาคต การใช้ Tailwind scale step (`4xl`) ตรงตาม convention ที่โค้ดเบสใช้อยู่แล้วและยังเผื่อพื้นที่มากกว่าจำเป็นเล็กน้อยไว้ safety margin
- *ไม่แก้ความกว้างเลย พึ่ง Decision 1 อย่างเดียว* — Decision 1 แก้แค่ "ต้องเลื่อนดูได้" แต่ไม่ได้ลดความถี่ที่ต้องเลื่อน ซึ่งยังเป็น UX ที่ไม่ดี (ตามที่ยืนยันจาก user ว่าเจอปัญหานี้จริงในการใช้งาน) จึงทำทั้งสอง decision ควบคู่กัน

## Risks / Trade-offs

- **[Risk]** `overflow-x:auto` ทำให้การ์ดมี scrollbar แนวนอนของตัวเองซ้อนกับ scrollbar ของ iframe เอง (ถ้า iframe เองก็ overflow ด้วย) กลายเป็น scrollbar ซ้อน 2 ชั้น **[Mitigation]** ในทางปฏิบัติ iframe (`className="w-full" style={{height:560}}`) ไม่ค่อยมีเหตุ overflow ของตัวมันเองอีกต่อไปหลัง bug#2 fix (เพราะเนื้อหาที่กว้างผิดปกติมักมาจาก template เต็มซึ่ง bypass การ์ดนี้ไปแล้ว) ส่วนเนื้อหาพิมพ์เอง/ตารางที่กว้างเกินจะ scroll ที่ระดับการ์ดเป็นหลัก ความเสี่ยง scrollbar ซ้อนจึงต่ำ
- **[Risk]** ขยาย dialog เป็น `sm:max-w-4xl` อาจทำให้ dialog ดูใหญ่เทอะทะขึ้นเล็กน้อยบนจอที่กว้างมากๆ **[Mitigation]** เป็นการขยับ scale step เดียว (768→896px) ไม่ใช่การเปลี่ยนขนาดแบบก้าวกระโดด และ dialog นี้มีแค่ preview + ปุ่ม 2 ปุ่ม ไม่มี layout ที่จะดู "โหว่" จากการขยายกว้างขึ้นเล็กน้อย
- **[Risk]** ยังมี viewport ที่แคบกว่า 600px+padding อยู่ดี (เช่น มือถือ) ที่ยังต้องเลื่อนแนวนอนอยู่ **[Mitigation]** ตามที่ระบุใน Non-Goals ยอมรับพฤติกรรมนี้เป็นปกติ ตรงกับที่ email client จริงทำ ไม่ใช่บั๊ก

## Migration Plan

- เป็นการแก้โค้ด frontend ล้วน (1 inline style + 1 Tailwind class) ไม่มี database migration ไม่มี breaking change ต่อ API
- Deploy ตามรอบ build ปกติ (`pnpm build`)
- ทดสอบด้วยมือก่อนปิดงาน: แทรกตารางกว้างในตัวแก้ไข (หลายคอลัมน์) → เปิดแท็บ "ตัวอย่าง" → ยืนยันเลื่อนแนวนอนเห็นคอลัมน์ท้ายๆ ได้ (ไม่ใช่หายไปเลย) → เปิดไดอะล็อก "ดู" template บนวิวพอร์ตขนาดต่างๆ (ปรับ resize_window) → ยืนยันบนวิวพอร์ต ≥1024px ไม่ต้องเลื่อนเลย
- Rollback: revert commit เดียว ไม่มี state เปลี่ยนแปลงถาวรฝั่ง backend/DB ให้ต้อง rollback เพิ่ม
