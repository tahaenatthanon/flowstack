## Why

โพสต์ที่เผยแพร่ออกไปมี HTML ดิบติดไปด้วย — พบจากโพสต์จริงบนเพจ Facebook เมื่อ 2026-08-25 ที่ `message` ขึ้นต้นด้วย `<article class="prose prose-sm max-w-none">` แล้วมี `<h1>`, `<p>`, `<li>` และ entity ที่ไม่ถูกถอดรหัส (`&#039;`) ปนอยู่ทั้งโพสต์ ต้นเหตุอยู่ที่บรรทัดเดียว: `api/lib/publish-dispatch.php:30` เขียนว่า

```php
$body = $art['html'] ?? $content['caption'] ?? '';
```

ลำดับ fallback นี้ทำให้เกิดปัญหา **สองชั้นที่ทับกัน** และชั้นที่สองใหญ่กว่าอาการที่มองเห็น:

1. **HTML ไม่ถูกแปลงเป็นข้อความ** — ค่า `article_content.html` ถูกยัดเข้า `message` ตรง ๆ ไม่มีการ strip tag หรือ decode entity ที่ใดในเส้นทาง
2. **แคปชั่นที่เขียนไว้สำหรับโซเชียลถูกทิ้งเงียบ ๆ** — เมื่อคอนเทนต์มีบทความอยู่ `$art['html']` ชนะทุกครั้ง `$content['caption']` จึงไม่เคยถูกใช้เลย

วัดจากข้อมูลจริงในตาราง `content_items` (34 แถว):

| | `caption` | `article_content.html` |
|---|---|---|
| ความยาว (อักษร) | 284 – 1,415 (เฉลี่ย 749) | 1,014 – 6,360 (เฉลี่ย 3,615) |
| รูปแบบ | ข้อความล้วน ไม่มี HTML | HTML บทความ SEO |
| จำนวนแถวที่มี | 31 | 23 |

มี 20 แถวที่มีทั้งสองค่า — ทั้ง 20 แถวนี้ระบบเลือกบทความ HTML ไปโพสต์ แทนแคปชั่นที่เขียนมาเพื่อโซเชียลโดยเฉพาะ เพดานของ Facebook คือ 63,206 อักษรจึงไม่ตัดทิ้ง = บทความทั้งบทพร้อม markup ขึ้นเพจ ส่วน Twitter มีเพดาน 280 อักษร (`:506`) ซึ่ง **43 อักษรแรกหมดไปกับ `<article class="prose prose-sm max-w-none">` เพียงแท็กเดียว** เท่ากับ 15% ของโพสต์เป็น markup ก่อนจะมีเนื้อหาแม้แต่ตัวอักษรเดียว

บั๊กนี้มีอยู่ก่อน change `add-facebook-photo-post` และไม่เกี่ยวกับรูป — กระทบทั้งโพสต์ที่มีรูปและไม่มีรูปเท่ากัน จึงบันทึกไว้เป็นงานแยกและมาแก้รอบนี้

## What Changes

- **แยกแหล่งเนื้อหาตามกลุ่มปลายทาง** ที่ `dispatch_content()` — แพลตฟอร์มโซเชียล (`facebook`, `instagram`, `tiktok`, `lineoa`, `linkedin`, `twitter`) SHALL ได้ body ที่เป็นข้อความล้วน โดยใช้ `caption` ก่อน แล้ว fallback ไป HTML ที่แปลงเป็นข้อความ; แพลตฟอร์มเว็บ/CMS (`wordpress`, `lotusdomino`, `custom`) ยังได้ HTML เดิมไม่เปลี่ยน เพราะปลายทางเรนเดอร์ HTML เป็นเนื้อหาบทความ
- **เพิ่มตัวแปลง HTML → ข้อความ** ในไฟล์เดียวกัน ที่รักษาโครงสร้างที่อ่านออก ไม่ใช่ `strip_tags()` เปล่า ๆ: `</p>`/`<br>`/`</h2>`–`</h6>` → ขึ้นบรรทัดใหม่, `<li>` → `• ` ขึ้นบรรทัด (**16 จาก 23 แถวมี `<li>`** — `strip_tags()` เพียว ๆ จะยุบรายการทั้งหมดเป็นข้อความติดกันอ่านไม่ออก), decode entity ด้วย `ENT_QUOTES | ENT_HTML5` (แก้ `&#039;` ที่เห็นบนโพสต์จริง), ยุบบรรทัดว่างซ้อนเหลือไม่เกินสองบรรทัด
- **ตัด `<h1>` นำหน้าออกเมื่อซ้ำกับหัวเรื่องที่จะถูกเติมอยู่แล้ว** — `dispatch_facebook():255` ประกอบ `message` เป็น `"$title\n\n$body"` ถ้าไม่ตัด หัวเรื่องจะปรากฏสองครั้งติดกัน วัดแล้วว่า **21 จาก 23 แถวมี `<h1>` และทั้ง 21 แถวมีข้อความใน `<h1>` ตรงกับ `$title` ที่ dispatcher ใช้แบบตัวต่อตัว**
- **ไม่แตะ `dispatch_wix()`** ซึ่งทำ `strip_tags($body)` ของตัวเองอยู่แล้วที่ `:594` — เป็นหลักฐานว่าปัญหานี้เคยถูกพบและแก้เฉพาะจุดมาก่อน แต่การแก้แบบนั้นไม่ครอบแพลตฟอร์มอื่นและยังยุบรายการอยู่ (บันทึกเป็นข้อจำกัดที่รู้อยู่ ไม่ใช่ขอบเขตรอบนี้)
- **ไม่มี BREAKING** — ไม่เปลี่ยน signature ของ `dispatch_*` ตัวใด ไม่เปลี่ยน schema ไม่เปลี่ยนสัญญาของ API ต่อฝั่งหน้าเว็บ

**ไม่อยู่ในขอบเขตรอบนี้:**
- ไม่แก้ `dispatch_wordpress()`, `dispatch_lotusdomino()`, `dispatch_custom()` — ทั้งสามรับ HTML ตามการออกแบบ การ strip จะทำให้บทความบนเว็บลูกค้าเสียรูป
- ไม่แก้ `dispatch_wix()` (ตัดสินใจร่วมกับผู้ใช้ให้จำกัดขอบเขตเฉพาะโซเชียล)
- ไม่แก้ตัวสร้างคอนเทนต์ให้เลิกใส่ `<h1>` หรือ wrapper `<article class="prose…">` ลงใน `article_content.html` — ต้นทางนั้นเป็นเรื่องของ SEO/preview บนเว็บ และกฎ `no_h1` ใน `api/lib/seo-checklist.php:100` ก็หักคะแนนให้อยู่แล้ว
- ไม่ย้อนแก้โพสต์ที่ออกไปแล้ว — ลบหรือแก้บนแพลตฟอร์มด้วยมือหากต้องการ

## Capabilities

### New Capabilities
- `publish-dispatch-plaintext-body`: กำหนดว่า body ที่ส่งให้แพลตฟอร์มโซเชียลต้องเป็นข้อความล้วน — ลำดับแหล่งข้อมูล (`caption` ก่อน แล้ว HTML ที่แปลงแล้ว), กฎการแปลง HTML → ข้อความที่รักษาย่อหน้าและรายการ, การถอดรหัส entity, การตัด `<h1>` ที่ซ้ำกับหัวเรื่อง และเส้นแบ่งว่าแพลตฟอร์มเว็บ/CMS ยังได้ HTML เดิม

### Modified Capabilities
ไม่มี — ตรวจ `openspec/specs/` ทั้งหมดแล้วไม่มี spec ใดกำหนดข้อกำหนดระดับ requirement ว่า body ของโพสต์มาจากแหล่งไหนหรือมีรูปแบบใด

`publish-dispatch-facebook-photo` ที่เพิ่งเพิ่มเข้ามา **ไม่ต้องแก้** — ข้อกำหนดในนั้นระบุว่า "เมื่อได้ `$title` และ `$body` มา ค่า `message` เป็น `"{title}\n\n{body}"` ตัดที่ 63,206 อักษร" ซึ่งพูดถึงการประกอบข้อความจากพารามิเตอร์ที่รับเข้ามา ไม่ได้พูดถึงว่า `$body` ถูกเลือกมาจากคอลัมน์ใด change นี้เปลี่ยนเฉพาะสิ่งที่ `dispatch_content()` ส่งเข้าไป ข้อกำหนดเดิมจึงยังเป็นจริงทุกข้อ

## Impact

- **แก้ไข:** `api/lib/publish-dispatch.php` ไฟล์เดียว — จุดเลือกแหล่ง body ที่ `:26-32` และเพิ่มฟังก์ชันแปลง HTML → ข้อความหนึ่งตัว ไม่แตะ `dispatch_*` ตัวใดเลยจึงไม่มีความเสี่ยงเรื่อง signature
- **ได้ผลทั้งสองเส้นเผยแพร่โดยไม่ต้องแก้เพิ่ม:** `api/content-publish.php` (`?action=send_now`) และ `api/cron/publish-scheduler.php` เรียก `dispatch_content()` ตัวเดียวกัน
- **มีจุดที่ต้องดูควบคู่:** `api/content-publish.php:179` สร้าง `article_content` ปลอมจาก override ของผู้ใช้ (`json_encode(['html' => $overrideText, …])`) ข้อความ override เป็นข้อความล้วนแต่ถูกใส่ในช่อง `html` — หลังแก้แล้วเส้นนี้ต้องยังได้ข้อความ override ตรงตามที่ผู้ใช้พิมพ์ ไม่ถูกแปลงเสียรูป นี่เป็นกรณีทดสอบบังคับ ไม่ใช่หมายเหตุ
- **ไม่มี migration:** ไม่แตะ schema ไม่แก้ข้อมูลเดิม
- **ไม่แก้ฝั่งหน้าเว็บ:** ไม่มีการเปลี่ยน UI, สถานะ, หรือ workflow อนุมัติ
- **ผลข้างเคียงที่ตั้งใจ:** โพสต์โซเชียลของคอนเทนต์ที่มีบทความจะสั้นลงมาก (จาก ~3,615 เหลือ ~749 อักษร) เพราะเปลี่ยนไปใช้แคปชั่นที่เขียนไว้ — เป็นเจตนาของ change นี้ ไม่ใช่การสูญหายของเนื้อหา
- **ผลต่อเกต SEO:** ไม่มี — `seo_gate_check()` อ่าน `article_content.html` จากคอนเทนต์โดยตรง ไม่ได้อ่านผ่านตัวแปร `$body` ของ dispatcher
