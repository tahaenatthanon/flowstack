## Context

การสร้างอีเมลแคมเปญใน `CampaignsPage.tsx` ทำได้ 2 แบบ:
1. เขียนเอาเองตั้งแต่ต้น (ไม่เลือก template) — ผู้ใช้พิมพ์เนื้อหาตรงๆ แล้ว `wrapEmailHtml()` ใน `api/email-utils.php` จะห่อ header (ชื่อบริษัท) + footer (ชื่อบริษัท + ข้อความแจ้งการสมัครรับข้อมูล) แบบทั่วไปให้ตอนส่งจริง เพื่อไม่ให้อีเมลออกไปแบบเปล่าๆ ไม่มีดีไซน์
2. เลือกจาก template สำเร็จรูป 1 ใน 20 แบบใน `src/data/emailTemplates.ts` — แต่ละอันเป็น HTML document เต็มรูปแบบ (`<!DOCTYPE html><html>...`) ที่มี header/footer ของตัวเองอยู่แล้ว

ตัว content editor (`ArticleEditor` ซึ่งใช้ TipTap) ใช้ร่วมกันทั้ง 2 แบบ TipTap ไม่รู้จัก `<!DOCTYPE>`/`<html>`/`<head>`/`<body>` ในตัว schema ของมัน พอผู้ใช้แตะ/พิมพ์ในช่องแก้ไข (ทำให้เกิดการเรียก `setContent()`/`getHTML()`) tag ห่อเหล่านี้จะหายไปทันที เหลือแค่เนื้อหาข้างในที่ TipTap รู้จักเป็น fragment ส่วน `wrapEmailHtml()` ตัดสินใจว่าจะห่อ chrome แบบทั่วไปเพิ่มหรือไม่ โดยเช็คแค่ว่ามีคำว่า `<html` หลงเหลืออยู่หรือเปล่า — เป็นวิธีเดาที่พังทันทีที่ editor แตะเนื้อหาที่มาจาก template เพราะสัญญาณที่ใช้ตัดสิน (`<html>` tag) คือสิ่งที่ TipTap ตัดทิ้งไปพอดี ผลคือ backend "ห่อให้" เนื้อหา template ที่มี header/footer ของตัวเองอยู่แล้วซ้ำอีกชั้น กลายเป็นอีเมลที่มี header 2 อัน footer 2 อัน

เรื่องนี้ยืนยันแล้วจากการส่งจริงไป Gmail: แคมเปญที่ไม่ได้เปิดแท็บแก้ไขเลย (`ทดสอบ 10`) ยังมี `<!DOCTYPE html><html>` ครบใน `body_html` และแสดงผลถูกต้อง ส่วนแคมเปญที่เปิด/แก้ไขแท็บนั้น (`ทดสอบ 11`) `body_html` ถูกลดเหลือแค่ fragment `<table>` เปล่าๆ และแสดงผลด้วย chrome ซ้อนกัน

## Goals / Non-Goals

**Goals:**
- กำจัด header/footer ที่ซ้อนกันสำหรับแคมเปญที่สร้างจาก template สำเร็จรูป ไม่ว่าผู้ใช้จะแก้ไขเนื้อหาภายหลังหรือไม่
- คงพฤติกรรมเดิมไว้สำหรับแคมเปญที่เขียนขึ้นเองตั้งแต่ต้น (ยังคงได้รับการห่อแบบทั่วไป)
- ทำให้การตัดสินใจ "ควรห่อไหม" เป็นค่าที่ชัดเจนแน่นอน แทนการเดาจากโครงสร้าง HTML ที่หลงเหลืออยู่

**Non-Goals:**
- การแก้ปัญหาดีไซน์เพี้ยน (gradient, shadow, ไอคอนที่จัดกลางด้วย flex) ที่ TipTap ตัดทิ้งไปด้วยจาก template HTML — เรื่องนี้ต้องแยก chrome ของ template ออกจากเนื้อหาที่แก้ไขได้ (โครงสร้างใหญ่กว่านี้) ซึ่งอยู่นอกขอบเขตของการแก้ครั้งนี้
- ไม่แก้ไขตัว editor (TipTap/`ArticleEditor`) เอง
- ไม่แก้ไข `buildEmailPreviewHtml()` (ตัวแสดงตัวอย่างในแท็บ preview ฝั่ง frontend) ซึ่งเป็นคนละ code path จาก backend ตอนส่งจริง และยังไม่มีรายงานว่ามีปัญหา
- ไม่ย้อนแก้แคมเปญที่ส่งไปแล้วในอดีต

## Decisions

**Decision: เพิ่มคอลัมน์ `template_id` ในตาราง `email_campaigns` แล้วใช้เป็นสัญญาณเดียวในการตัดสินว่าจะห่อหรือไม่**

- ทางเลือกที่เคยพิจารณา: ทำให้ `wrapEmailHtml()` ฉลาดขึ้นในการเดา (เช่น ดูโครงสร้าง table ที่ลึกเป็นพิเศษ หรือแทรก HTML comment เป็น marker เช่น `<!--template-->` กลับเข้าไปในเนื้อหา) — ปฏิเสธแนวทางนี้ เพราะ TipTap อาจตัด HTML comment ทิ้งได้เช่นกัน และการเดาจากเนื้อหาแบบไหนก็เปราะบางโดยธรรมชาติ จะพังอีกทันทีที่ output ของ editor เปลี่ยนรูปแบบ การใช้ flag ที่ชัดเจนและบันทึกไว้ตั้งแต่ตอนเลือก template จะไม่มีความกำกวมและไม่ขึ้นกับว่าอะไรรอดจากการ round-trip ผ่าน editor
- ทางเลือกที่เคยพิจารณา: เก็บ `template.html` ดิบที่ยังไม่ผ่านการแก้ไขแยกไว้ต่างหากจาก `campaignBody` ที่ผู้ใช้แก้ไข แล้วส่งเวอร์ชันดิบนั้นเสมอ — ปฏิเสธสำหรับการแก้ครั้งนี้ เพราะจะทำให้การแก้ไขของผู้ใช้ภายใน template ไม่ถูกนำไปใช้ในอีเมลที่ส่งจริงเลย ขัดกับจุดประสงค์ของแท็บแก้ไข (แนวทางนี้ใกล้เคียงกับ Option B ที่เคยคุยกันไว้ คือแยก chrome ออกจากเนื้อหา — ขอบเขตใหญ่กว่า)
- `template_id` เป็น nullable เก็บ id ของ template แบบ static string จากฝั่ง frontend (เช่น `template-5`) — ไม่ใช่ foreign key เพราะ template ใน `emailTemplates.ts` เป็นข้อมูล static ฝั่ง frontend ไม่มีตาราง DB รองรับ

**Decision: การข้ามการห่อเกิดขึ้นที่ send path (`api/email-campaigns.php`) ไม่ใช่การเปลี่ยนพฤติกรรม default ของ `wrapEmailHtml()`**

- `wrapEmailHtml()` ยังคงพฤติกรรม default เดิม (ห่อเสมอ เว้นแต่จะถูกบอกไม่ให้ห่อ) เพราะอาจมีจุดเรียกใช้อื่นในอนาคตที่ไม่มี template ผู้เรียกใช้ในขั้นตอนส่งจะอ่านค่า `template_id` แล้วข้ามการเรียก `wrapEmailHtml()` ไปเลยเมื่อมีค่า โดยใช้ `$rawHtml` ตรงๆ

## Risks / Trade-offs

- [ความเสี่ยง] แคมเปญที่เริ่มจาก template แล้วผู้ใช้ลบ markup ของ template ออกหมดแล้วพิมพ์เนื้อหาใหม่ทั้งหมด — `template_id` ยังคงมีค่าอยู่ ทำให้ไม่มีการห่อแบบทั่วไป อาจส่งเนื้อหาที่ไม่มีดีไซน์ออกไป → **การรับมือ**: เป็น edge case ที่แม้แต่ flow "เขียนเอง" ก็จะได้ผลลัพธ์ไม่ดีเหมือนกันถ้าข้ามการห่อ ยอมรับได้เมื่อเทียบกับทางเลือกอื่นที่จะทำให้ case หลักพัง (บันทึกไว้เป็นข้อจำกัดที่รู้อยู่แล้ว ไม่ได้แก้แบบเงียบๆ)
- [ความเสี่ยง] แคมเปญเก่าที่ส่ง/ร่างไว้ก่อนการแก้ครั้งนี้จะมี `template_id = NULL` แม้จะมาจาก template จริงก็ตาม → **การรับมือ**: ไม่สามารถ backfill ย้อนหลังได้ (frontend ไม่เคยบันทึกไว้ก่อนหน้านี้ว่าใช้ template ไหน) กระทบแค่การแสดงประวัติแคมเปญเก่า ไม่กระทบการส่งแคมเปญใหม่ในอนาคต
- [Trade-off] ไม่แก้ปัญหาดีไซน์เพี้ยนจากการที่ TipTap ตัด layout แบบ `<div>` ทิ้ง (เช่น วงกลมไอคอนที่จัดกลางด้วย flex) ยอมรับว่าอยู่นอกขอบเขต และระบุไว้ใน proposal ว่าเป็นงานต่อยอด (Option B)

## Migration Plan

1. สร้าง migration `database/migrations/<timestamp>_add_template_id_to_email_campaigns.sql`: `ALTER TABLE email_campaigns ADD COLUMN template_id VARCHAR(64) NULL AFTER source_content_id;`
2. รันกับ MariaDB local ตามข้อกำหนดของโปรเจกต์ แล้วตรวจสอบด้วย `DESCRIBE email_campaigns`
3. แก้ handler สร้าง/แก้ไขแคมเปญใน `api/email-campaigns.php` ให้รับและบันทึกค่า `template_id` จาก request body
4. แก้ handler ตอนส่งให้อ่านค่า `template_id` แล้วข้าม `wrapEmailHtml()` ตามเงื่อนไข
5. แก้ `CampaignsPage.tsx` ให้ส่ง `template_id: selectedTemplate || null` ไปใน payload ตอนสร้าง/แก้ไข
6. ทดสอบด้วยมือ: (a) ส่งแคมเปญที่มาจาก template หลังแก้ไขเนื้อหาในแท็บแก้ไข — ต้องมี header/footer แค่ชุดเดียว (b) ส่งแคมเปญที่เขียนเองตั้งแต่ต้น — ยังคงมีการห่อแบบทั่วไปเหมือนเดิม

Rollback: คอลัมน์เป็นแบบ additive และ nullable การย้อนแก้โค้ด PHP/frontend ก็เพียงพอแล้ว ปล่อยคอลัมน์ไว้เฉยๆ โดยไม่ใช้งานก็ไม่มีผลเสีย
