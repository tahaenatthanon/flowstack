## Context

`dispatch_content()` (`api/lib/publish-dispatch.php:13`) เป็นจุดเดียวที่แปลงแถว `content_items` ให้เป็นพารามิเตอร์ของ dispatcher ทุกแพลตฟอร์ม ทั้งเส้น `send_now` (`api/content-publish.php`) และเส้น cron (`api/cron/publish-scheduler.php`) ผ่านที่นี่ทั้งคู่ — แก้ที่นี่จุดเดียวจึงครอบทั้งสองเส้น

บรรทัดที่เป็นต้นเหตุคือ `:30`:

```php
$title   = $art['title']   ?? $content['title']   ?? '';
$body    = $art['html']    ?? $content['caption'] ?? '';   // ← ปัญหาอยู่ที่นี่
```

`$body` ตัวเดียวถูกแจกให้ทุกแพลตฟอร์มใน `match` ที่ `:46-58` โดยไม่แยกว่าปลายทางเรนเดอร์ HTML ได้หรือไม่:

| กลุ่ม | แพลตฟอร์ม | ปลายทางต้องการ | สภาพปัจจุบัน |
|---|---|---|---|
| โซเชียล | facebook, instagram, tiktok, lineoa, linkedin, twitter | ข้อความล้วน | **ได้ HTML ดิบ → บั๊ก** |
| เว็บ/CMS | wordpress, lotusdomino, custom | HTML | ถูกต้องอยู่แล้ว |
| กึ่งกลาง | wix | ข้อความล้วน | strip เองที่ `:594` |

ข้อเท็จจริงที่บังคับรูปร่างของทางแก้ (วัดจาก `content_items` 34 แถว):

1. dispatcher โซเชียลทั้ง 6 ตัวเติมหัวเรื่องด้วยสำนวนเดียวกันหมด — `$title ? "$title\n\n$body" : $body` ที่ `:255`, `:338`, `:385`, `:425`, `:454`, `:505` — ดังนั้นถ้า body ยังมี `<h1>` ที่ซ้ำกับหัวเรื่อง ผลคือหัวเรื่องซ้ำสองครั้งติดกันทุกแพลตฟอร์ม ไม่ใช่แค่ Facebook
2. `<h1>` ใน `article_content.html` 21 แถว มีข้อความ **ตรงกับ `$title` ที่ dispatcher ใช้ (`$art['title'] ?? $content['title']`) ทั้ง 21 แถวแบบตัวต่อตัว** — ถ้าเทียบกับคอลัมน์ `title` เพียว ๆ จะตรงแค่ 16 แถว เพราะ 5 แถวมี `article_content.title` ที่ยาวกว่าและชนะใน fallback ลำดับการเทียบจึงต้องใช้ค่า `$title` ที่คำนวณแล้ว ไม่ใช่คอลัมน์ดิบ
3. 16 จาก 23 แถวมี `<li>` — `strip_tags()` เปล่า ๆ จะยุบรายการเป็นข้อความติดกันเป็นพืด
4. `caption` (284–1,415 อักษร เฉลี่ย 749) เป็นข้อความล้วนไม่มี HTML เลย ขณะที่ `article_content.html` เป็น HTML 1,014–6,360 อักษร เฉลี่ย 3,615 — ต่างกันประมาณ 5 เท่า และแถวที่ยาวสุดแปลงเป็นข้อความล้วนได้ 5,407 อักษร ซึ่งยังเกินเพดาน instagram/tiktok (2,200) และ twitter (280)
5. 0 แถวมี `<script>` หรือ `<style>` (ตรวจแล้ว) แต่ `strip_tags()` เก็บ **ข้อความข้างใน** แท็กเหล่านั้นไว้ ถ้าวันหนึ่งมี CSS/JS จะไหลไปโพสต์บนเพจสาธารณะ

## Goals / Non-Goals

**Goals:**
- โพสต์บนแพลตฟอร์มโซเชียลต้องไม่มี HTML tag หรือ HTML entity ที่ไม่ถูกถอดรหัสหลงไป
- ใช้เนื้อหาที่เขียนไว้สำหรับโซเชียลจริง (`caption`) เมื่อมี ไม่ใช่บทความ SEO ขนาดยาว
- เนื้อหาที่แปลงจาก HTML ต้องยังอ่านออก — ย่อหน้ากับรายการต้องไม่ถูกยุบ
- แพลตฟอร์มเว็บ/CMS ต้องได้ HTML เหมือนเดิม 100% — เป็นเกณฑ์ตัดสินว่าไม่เกิด regression
- ตรวจได้ก่อนยิงออกภายนอก — เห็นข้อความสุดท้ายของทุกแถวได้โดยไม่ต้องโพสต์จริง

**Non-Goals:**
- ไม่ย่อ/สรุปบทความให้สั้นลงพอสำหรับโซเชียล — แถวที่ไม่มี `caption` (3 แถว) จะยังได้บทความทั้งบทในรูปข้อความล้วน การย่อต้องใช้การตัดสินใจเชิงผลิตภัณฑ์ (จะตัดที่กี่อักษร ต่อท้ายด้วยลิงก์อะไร) ซึ่งยังไม่มีคำตอบและไม่มีคอลัมน์ URL บทความให้ใช้
- ไม่แก้ตัวสร้างคอนเทนต์ให้เลิกใส่ `<h1>` / `<article class="prose…">` ลงใน `article_content.html`
- ไม่แก้ `dispatch_wix()` (ตัดสินใจร่วมกับผู้ใช้ให้จำกัดเฉพาะโซเชียล)
- ไม่ทำ HTML sanitizer สำหรับ HTML ที่ไม่น่าเชื่อถือ — HTML ทั้งหมดมาจากตัวสร้างของระบบเอง
- ไม่แตะ schema ไม่มี migration ไม่แก้ข้อมูลเดิม ไม่แก้ฝั่งหน้าเว็บ
- ไม่แก้เพดานความยาวต่อแพลตฟอร์ม (`mb_substr` ที่มีอยู่) และไม่แก้การตัดกลางคำที่เป็นพฤติกรรมเดิม

## Decisions

### 1. แยกตัวแปรสองตัวที่ `dispatch_content()` ไม่ใช่แก้ในแต่ละ dispatcher

คำนวณทั้งสองค่าไว้ที่จุดเดียวแล้วเลือกส่งใน `match`:

```php
$body       = $art['html'] ?? $content['caption'] ?? '';   // คงเดิม — เว็บ/CMS ใช้ค่านี้
$socialBody = ...;                                          // ใหม่ — โซเชียล 6 ตัวใช้ค่านี้
```

ทางเลือกที่พิจารณาแล้วตัดออก:

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| strip ในแต่ละ dispatcher โซเชียล | ต้องแก้ 6 ฟังก์ชัน ซ้ำโค้ดเดียวกัน 6 รอบ และแพลตฟอร์มที่เพิ่มในอนาคตจะลืมได้ง่าย — เป็นแบบที่ `dispatch_wix()` ทำอยู่แล้วและพิสูจน์แล้วว่าไม่ครอบ |
| เขียนทับ `$body` ให้เป็นข้อความล้วนไปเลยทั้งหมด | ทำให้บทความบนเว็บลูกค้า (lotusdomino/wordpress) เสียรูปทั้งหมด — เป็นการพังของจริงที่ร้ายกว่าบั๊กเดิม |
| แปลงตอนบันทึกคอนเทนต์ (เพิ่มคอลัมน์ข้อความล้วน) | ต้อง migration + backfill 23 แถว และ HTML แก้ได้ทีหลังทำให้ค่าที่ backfill ไว้เก่า — เก็บเป็นการคำนวณตอน dispatch ตรงกว่า |

การเลือกเกิดใน `match` arm ที่ต่างกันอยู่แล้ว จึงอ่านออกจากโค้ดตรง ๆ ว่าแพลตฟอร์มไหนได้ค่าไหน — ตรงตามกฎ NO MAGIC ไม่มีการแปลงที่มองไม่เห็น

### 2. `caption` มาก่อน แล้ว fallback เป็น HTML ที่แปลงเป็นข้อความ

```
$socialBody = trim($content['caption'] ?? '') !== ''
    ? trim($content['caption'])
    : publish_html_to_text($art['html'] ?? '', $title);
```

เหตุผลที่ไม่ใช่ "แปลง HTML เสมอ": การแปลงแก้ปัญหา tag แต่ไม่แก้ปัญหา **เนื้อหาผิดชนิด** — บทความ 3,615 อักษรที่แปลงเป็นข้อความแล้วก็ยังเป็นข้อความยาวหลายพันอักษรบนโพสต์โซเชียล เกินเพดาน instagram/tiktok (2,200) และบน Twitter (เพดาน 280) จะถูกตัดกลางประโยคที่ย่อหน้าแรก ส่วน `caption` เขียนมาเพื่องานนี้อยู่แล้ว 20 แถวที่มีทั้งสองค่าจึงได้ค่าที่ถูกต้องทันที

`trim()` ก่อนเทียบ เพื่อให้ caption ที่มีแต่ช่องว่างไม่ชนะ HTML ที่มีเนื้อหาจริง

ผลข้างเคียงที่จงใจ: caption ไม่ถูกแปลงเลย — ผู้ใช้พิมพ์อะไรได้อย่างนั้น ครอบเส้น override ที่ `api/content-publish.php:179` ซึ่งยัดข้อความล้วนของผู้ใช้ลงช่อง `html` ด้วย (เส้นนั้นตั้ง `caption` เป็นข้อความเดียวกัน จึงชนะที่ลำดับแรกและไม่ถูกแปลง)

### 3. แปลงแบบรักษาโครงสร้าง ไม่ใช่ `strip_tags()` เปล่า

ฟังก์ชันใหม่ `publish_html_to_text(string $html, string $dupTitle = ''): string` ทำตามลำดับนี้ — **ลำดับสำคัญ**:

1. ถ้า `$dupTitle` ไม่ว่าง → หา `<h1>` **ตัวแรก** เทียบข้อความข้างในกับ `$dupTitle` ถ้าตรงให้ลบทั้ง element ออก (ดูข้อ 4)
2. ลบ `<script>…</script>` และ `<style>…</style>` **พร้อมเนื้อข้างใน** — ต้องทำก่อน `strip_tags()` ซึ่งเก็บข้อความข้างในไว้
3. แปลงแท็กที่มีความหมายเชิงโครงสร้างเป็นตัวคั่นข้อความ: `<li>` → `\n• `, `<br>` → `\n`, ปิด `</p>` `</h1>`–`</h6>` `</div>` `</ul>` `</ol>` `</blockquote>` → `\n\n`
4. `strip_tags()` แท็กที่เหลือทั้งหมด (รวม `<article class="prose…">` ที่เป็น 43 อักษรแรกของทุกแถว)
5. `html_entity_decode($text, ENT_QUOTES | ENT_HTML5, 'UTF-8')` — **หลัง** strip ไม่ใช่ก่อน เพื่อไม่ให้ `&lt;` ที่ถอดรหัสแล้วกลายเป็นแท็กจริงที่ถูกกินในขั้นถัดไป ลำดับนี้ตรงกับ `seo_word_count()` ที่ `api/lib/seo-checklist.php:199` ซึ่งเป็นสำนวนที่ใช้อยู่แล้วในโปรเจกต์
6. normalize: `\r\n` → `\n`, ยุบช่องว่าง/แท็บซ้อน, ยุบ `\n` สามบรรทัดขึ้นไปเหลือสองบรรทัด, `trim()`

ใช้ `•` (U+2022) เป็นสัญลักษณ์รายการ — ทุกปลายทางรับ UTF-8 และเพดานต่อแพลตฟอร์มนับด้วย `mb_substr()` แบบอักษร จึงไม่มีปัญหาเรื่องไบต์

### 4. ตัด `<h1>` ตัวแรกเมื่อซ้ำกับ `$title` ที่จะถูกเติมอยู่แล้ว

เทียบกับ `$title` ที่ `dispatch_content():29` คำนวณได้ (`$art['title'] ?? $content['title']`) **ไม่ใช่คอลัมน์ `title`** — วัดแล้วว่าถ้าเทียบกับคอลัมน์ดิบจะพลาด 5 แถวที่ `article_content.title` ยาวกว่าและชนะใน fallback ซึ่งเป็นค่าที่โพสต์จริงใช้ เทียบกับค่าที่คำนวณแล้วได้ 21/21

เทียบแบบ normalize ทั้งสองฝั่ง: strip tag ข้างใน `<h1>` → decode entity → `trim()` ไม่เทียบสตริงดิบ เพราะ `<h1>` มักมี attribute และ entity อยู่ข้างใน

ตัดเฉพาะตัวแรกและเฉพาะเมื่อตรง — `<h1>` ตัวถัดไป (ถ้ามี) แปลงเป็นบรรทัดข้อความปกติ ไม่ตัด เพราะไม่ได้ซ้ำกับหัวเรื่องและเป็นเนื้อหาที่ผู้ใช้อนุมัติมา การตัดทุก `<h1>` จะเป็นการลบเนื้อหาโดยไม่มีเหตุผลรองรับ

ไม่ตัดเมื่อไม่ตรง — ยอมให้หัวเรื่องสองแบบอยู่ในโพสต์เดียวดีกว่าลบข้อความที่อาจไม่ซ้ำ

### 5. เว็บ/CMS ไม่แตะเลย และ wix ไม่แตะเช่นกัน

`dispatch_wordpress()` (`:564` `'content' => $body`), `dispatch_lotusdomino()` (`:644` `'Body' => $body`), `dispatch_custom()` (`:693` `'content' => $body`) ยังรับ `$body` ตัวเดิม — ปลายทางเรนเดอร์ HTML เป็นบทความ

`dispatch_wix()` ที่ `:594` ทำ `strip_tags($body)` ของตัวเองอยู่แล้ว ปล่อยไว้ตามที่ตกลง — ผลคือ wix จะยังยุบรายการและไม่ decode entity ต่างจากโซเชียล บันทึกเป็นความไม่สอดคล้องที่รู้อยู่ ไม่ใช่ของที่ลืม

## Risks / Trade-offs

**[โพสต์สั้นลงมากจนดูเหมือนเนื้อหาหาย] → เป็นเจตนา และผู้อนุมัติเห็น caption อยู่ก่อนแล้ว**
20 แถวที่มีทั้งสองค่าจะเปลี่ยนจาก ~3,615 อักษรเหลือ ~749 อักษร ต้องสื่อสารให้ชัดว่านี่คือการใช้แคปชั่นที่เขียนไว้ ไม่ใช่การตัดเนื้อหาทิ้ง — หน้ารายละเอียดอนุมัติแสดงทั้งบทความและแคปชั่นอยู่แล้ว (spec `approval-detail-full-content`) ผู้อนุมัติจึงเห็นสิ่งที่จะถูกโพสต์

**[3 แถวที่ไม่มี `caption` จะยังได้บทความทั้งบท] → แก้เรื่อง tag ได้ แต่ไม่แก้เรื่องความยาว**
แถวเหล่านั้นจะได้ข้อความล้วนที่อ่านออก แต่ยาวเท่าเดิมและถูกตัดด้วยเพดานต่อแพลตฟอร์มตามกลไกเดิม — อยู่ใน Non-Goals อย่างชัดแจ้ง ไม่ใช่ของที่พลาด

**[`strip_tags()` กับ HTML ที่ผิดรูปจะกินข้อความระหว่าง `<` ที่ไม่ปิด] → HTML มาจากตัวสร้างของระบบเอง**
ไม่ได้ทำ sanitizer สำหรับ HTML ที่ไม่น่าเชื่อถือ และเส้นที่ผู้ใช้พิมพ์เอง (caption/override) ไม่ผ่านการแปลงเลยจึงไม่ได้รับผลนี้ ถ้าอนาคตรับ HTML จากภายนอกต้องทบทวนใหม่

**[ตัด `<h1>` ผิดตัวแล้วเนื้อหาหาย] → เงื่อนไขแคบและตรวจได้ครบทุกแถวก่อนโพสต์**
ตัดเฉพาะ `<h1>` ตัวแรกที่ข้อความตรงกับหัวเรื่องเป๊ะ ถ้าไม่ตรงไม่ตัด และตรวจผลของทั้ง 23 แถวได้ด้วยสคริปต์ที่ไม่ยิงคำขอออกไปเลย

**[`<script>`/`<style>` ยังไม่เคยมีจริง] → ป้องกันไว้ล่วงหน้าด้วยต้นทุน 1 บรรทัด**
วัดแล้วได้ 0 แถว การเพิ่มการลบทิ้งจึงเป็นการป้องกัน ไม่ใช่การแก้อาการที่พบ — ระบุไว้ตรง ๆ เพื่อไม่ให้เข้าใจผิดว่าเคยเกิด

**[เส้น override ที่ `content-publish.php:179` อาจถูกแปลงเสียรูป] → caption-first ครอบให้แล้ว แต่ต้องทดสอบจริง**
เส้นนั้นตั้งทั้ง `caption` และ `article_content.html` เป็นข้อความ override เดียวกัน ลำดับ caption-first ทำให้ได้ข้อความตรงตามที่ผู้ใช้พิมพ์โดยไม่ผ่านตัวแปลง — เป็นกรณีทดสอบบังคับ ไม่ใช่การอนุมานว่าคงจะถูก

**[`send_now` ไม่มี dry-run] → ตรวจให้จบด้วยสคริปต์ก่อน แล้วยิงจริงครั้งเดียว**

## Open Questions

ไม่มีข้อที่บล็อกการลงมือ — ข้อด้านล่างเป็นการตัดสินใจเชิงผลิตภัณฑ์ที่รอได้ และตั้งใจปล่อยไว้นอกขอบเขต

- แถวที่มีแต่ `article_content` ไม่มี `caption` (3 แถว) ควรถูกย่อก่อนโพสต์โซเชียลหรือไม่ และถ้าย่อ ควรต่อท้ายด้วยลิงก์บทความ — ยังไม่มีคอลัมน์ URL บทความให้ใช้ จึงยังตอบไม่ได้ ตอนนี้ปล่อยให้เพดานต่อแพลตฟอร์มตัดตามกลไกเดิม
- ควรบังคับให้ต้องมี `caption` ก่อนอนุมัติโพสต์โซเชียลหรือไม่ — เป็นเรื่องของเกตอนุมัติ ไม่ใช่ชั้น dispatch
- `dispatch_wix()` ควรรวมมาใช้ตัวแปลงเดียวกันเมื่อไรจึงจะคุ้ม — รอบนี้ตกลงกันว่าไม่แตะ
