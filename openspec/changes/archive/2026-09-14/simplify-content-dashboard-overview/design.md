## Context

แท็บ "ภาพรวม" ของ `ContentDashboardPage` สะสม widget ผ่านหลาย PR (ดู git log: `319dd37` เพิ่ม BI widgets, `695e6d4` เพิ่ม result metrics, `eaa58ed` sync facebook metrics ฯลฯ) โดยแต่ละ widget เพิ่มเข้ามาแยกกัน ไม่มีใครกลับมาตัดของที่ซ้ำซ้อนออก ผลคือหน้านี้มี 9 widget + stat card 4 ใบที่ดึงจาก 4 แหล่งข้อมูลต่างกัน (`content_items` ฝั่ง client, `content_publish_queue`, funnel ตาม timestamp, aging, asset-gen, channels) และมีจุดที่ตัวเลขซ้ำกันเอง 3 จุด (stat card ↔ work-progress, รออนุมัติ list ↔ รออนุมัติ stat, overdue banner ↔ overdue ในการ์ดคิว)

งานนี้เกิดจากการสำรวจร่วมกับผู้ใช้ (developer3@ktnbs.com) ผ่าน `/opsx:explore` โดยตกลงร่วมกันว่า:
- กลุ่มเป้าหมายหลักของหน้านี้คือผู้ดูแล/อนุมัติคอนเทนต์ ไม่ใช่ทีมผลิตหรือผู้บริหาร
- ให้เก็บ "สถานะปัจจุบัน" (snapshot) แทน "Funnel สะสม" เพราะสองอย่างนี้เล่าเรื่องคล้ายกันแต่ตัวเลขไม่ตรงกันเสมอไป (เช่น item ที่เคยอนุมัติแล้วถูกตีกลับ draft) และ snapshot ตรงกับสิ่งที่ต้องติดตาม ("ตอนนี้อยู่ไหน") มากกว่า
- UI ต้องยึดตามรูปแบบที่ระบบใช้อยู่แล้วทั้งระบบ ไม่ใช่คิดลายใหม่เฉพาะหน้านี้

## Goals / Non-Goals

**Goals:**
- ลดจำนวนแหล่งความจริงของตัวเลขสถานะคอนเทนต์เหลือจุดเดียว (การ์ด "ความคืบหน้าการผลิต")
- แยกสิ่งที่ต้องการ "การตัดสินใจ" (อนุมัติ/ลองส่งใหม่) ออกจากสิ่งที่เป็น "ข้อมูลอ้างอิง" ด้วยการจัดกลุ่มเป็น 2 คอลัมน์ตามจุดประสงค์
- คงความสอดคล้องกับ pattern ภาพ/โครงสร้างที่มีอยู่แล้วทั้งระบบ (ไม่เพิ่มลายใหม่)
- ไม่แตะ backend/schema — งานนี้เป็นการจัดเรียง/ตัดทอนฝั่ง frontend ล้วนๆ

**Non-Goals:**
- ไม่ปรับ query หรือ endpoint `api/content-analytics.php` (ทุกฟิลด์ที่ frontend เคยใช้ยังคงถูกส่งกลับเหมือนเดิม แค่ frontend เลือกไม่ render บางส่วน)
- ไม่แตะแท็บ "วิเคราะห์" ยกเว้นการรับ widget "สถานะช่องทาง" ที่ย้ายเข้ามา
- ไม่แก้ spec drift เดิมที่มีอยู่ก่อนงานนี้ (เช่น `content-dashboard-stat-card-style` ที่ปนตัวอย่างสีของ stat card 2 ตำแหน่งเข้าด้วยกัน) เกินขอบเขตที่งานนี้ต้องแตะ

## Decisions

### 1. ยุบ stat card 4 ใบเข้ากับการ์ดสถานะ แทนที่จะเก็บไว้คู่กัน
**เลือก**: ลบ `productionStatCards` grid ทั้งหมด ให้การ์ด "ความคืบหน้าการผลิต" (`workProgressStatuses`) เป็นแหล่งเดียวของทั้งจำนวนรวมและสัดส่วนสถานะ
**ทางเลือกที่ไม่เลือก**: เก็บ stat card ไว้เป็นสรุปย่อบนสุด แล้วให้การ์ดสถานะเป็นรายละเอียด — ถูกตัดออกเพราะข้อมูลชุดเดียวกันแสดง 2 ที่ในหน้าเดียวสร้างภาระอ่านโดยไม่ได้ข้อมูลเพิ่ม (ผู้ใช้ยืนยันให้ยุบระหว่าง exploration)

### 2. เพิ่มสถานะ `rejected` เป็นสถานะที่ 6
**เลือก**: เพิ่ม `rejected` ต่อจาก 5 สถานะเดิมในลำดับที่แสดง โดยใช้สี/ไอคอนที่มีอยู่แล้วใน `STATUS_MAP.rejected` (`text-red-700`, ไอคอน `XCircle`) — ไม่ต้องออกแบบใหม่
**เหตุผล**: `rejected` เป็นสถานะจริงในระบบ ($content_items.status$ enum, ดู `2026_08_11_171224_refactor_content_status_enum.sql$) ใช้งานจริงใน `ContentApprovalTab.tsx` แต่ถูกมองข้ามจากการ์ดสถานะโดยไม่มีเหตุผล — สำหรับผู้อนุมัติ การเห็นว่ามีคอนเทนต์ถูกปฏิเสธค้างอยู่เท่าไหร่มีความหมายโดยตรงกับงานของเขา

### 3. ตัด Funnel การผลิต และ สถานะสร้างสื่อ AI แทนที่จะย้ายไปแท็บวิเคราะห์
**เลือก**: ตัดออกจาก UI เลย ไม่ย้ายไปที่ไหน (backend ยังคำนวณอยู่เผื่ออนาคต)
**ทางเลือกที่ไม่เลือก**: ย้ายไปแท็บวิเคราะห์เหมือน "สถานะช่องทาง" — ผู้ใช้ตัดสินใจว่า Funnel เล่าเรื่องซ้ำกับการ์ดสถานะ (สร้างความสับสนมากกว่าให้ข้อมูลเพิ่ม) และสถานะสร้างสื่อ AI เป็นรายละเอียดการผลิตที่ไม่ตรงกับ "ติดตามสถานะคอนเทนต์" ของผู้อนุมัติ จึงตัดทั้งคู่แทนที่จะย้าย

### 4. แยก "สุขภาพคิวเผยแพร่" เป็น 2 การ์ดตามจุดประสงค์
**เลือก**: การ์ด "เผยแพร่ล้มเหลว" (list + ปุ่มลองส่งใหม่, ต้องตัดสินใจ) → คอลัมน์ต้องดำเนินการ; การ์ด "คิวเผยแพร่" (นับ pending/processing/sent อย่างเดียว, ข้อมูลอ้างอิง) → คอลัมน์ภาพรวม
**เหตุผล**: ตัวนับ pending/processing/sent ไม่มี action ให้ทำ ต่างจากรายการ failed ที่มีปุ่ม "ลองส่งใหม่" — แยกตามว่าเป็น action หรือ reference สอดคล้องกับหลักการจัดกลุ่ม 2 คอลัมน์ของงานนี้ทั้งหมด

### 5. ตัดข้อความ "เลยกำหนด" ที่ซ้ำในการ์ดคิวเผยแพร่
**เลือก**: เหลือ banner บนสุดของหน้าเป็นจุดแจ้งเตือนเดียว (ใช้ `useOverdueCount()` เดิม), ตัด inline warning ในการ์ดคิวออก
**เหตุผล**: ทั้งสองจุดคำนวณจากนิยามเดียวกัน (`status='pending' AND scheduled_at < NOW()`) ตามที่ระบุไว้ใน comment ของ `content-analytics.php` เอง — แสดงซ้ำ 2 ที่ไม่ได้ข้อมูลเพิ่ม

### 6. สัดส่วนคอลัมน์คงเดิม 2:1 (ซ้ายกว้าง ขวาแคบ) ไม่สลับ
**เลือก**: คอลัมน์ "ต้องดำเนินการ" อยู่ซ้ายและใช้ `xl:col-span-2` (กว้าง) เหมือนโครงเดิมของหน้านี้, คอลัมน์ "ภาพรวม" อยู่ขวาใช้ `xl:col-span-1` (แคบ)
**ทางเลือกที่ไม่เลือก**: สลับเป็น 1:2 (ซ้ายแคบ) เพื่อให้สัดส่วนสอดคล้องกับจำนวนการ์ดที่เหลือน้อยกว่าฝั่งซ้าย — ถูกตีกลับหลังตรวจสอบโค้ดทั้งระบบ (`HomePage.tsx` บรรทัด 392-395, 697-700 และโครงเดิมของหน้านี้เอง) พบว่าทุกที่ใช้ col-span-2 สำหรับ "เนื้อหาหลัก/ละเอียด" เป็นมาตรฐานเดียวกันหมด ไม่มีที่ไหนกลับด้าน — การสลับจะสร้างลายใหม่ที่ไม่ตรงกับระบบ จึงคงของเดิมไว้แม้คอลัมน์ซ้ายจะมีการ์ดน้อยกว่า

### 7. ไม่ใช้ border-l-4 accent บนการ์ด ใช้ Badge ในหัวการ์ดแทน
**เลือก**: ใส่ `<Badge>` แสดงจำนวนใน `CardTitle` ของการ์ด "เผยแพร่ล้มเหลว" และ "คอนเทนต์ค้างท่อ" เท่านั้น ไม่เพิ่มกรอบสีด้านซ้าย (`border-l-4`)
**ทางเลือกที่ไม่เลือก**: ใส่ `border-l-4 border-l-red-500`/`border-l-amber-500` ตามที่เสนอไว้รอบแรก — ถูกตีกลับหลังพบว่า pattern นี้ใช้เฉพาะการ์ด kanban ที่ลากได้ (`Index.tsx`, `SalesPage.tsx`) เท่านั้น ไม่เคยใช้กับการ์ดสรุปแดชบอร์ดที่ไหนในระบบ ส่วน Badge-in-CardTitle มีตัวอย่างจริงรองรับ (`ImpactOSPage.tsx` บรรทัด 1379-1380) จึงใช้แทน

### 8. หัวข้อคอลัมน์ใช้ `<h3 className="text-sm font-semibold mb-3">`
**เลือก**: ใช้สไตล์เดียวกับหัวข้อกลุ่มการ์ดใน `BudgetPage.tsx` บรรทัด 489 (`ภาพรวมแต่ละโปรเจกต์`) แทนการคิด class ใหม่

### 9. ย้าย "สถานะช่องทาง" ไปแท็บวิเคราะห์ sub-tab โซเชียล
**เลือก**: วางเป็น widget แบบ snapshot (ไม่ผูกช่วงวันที่ที่เลือกในแท็บวิเคราะห์) ใน `AnalyticsSocialTab.tsx` ต่อจาก widget ที่มีอยู่
**เหตุผล**: เป็นข้อมูล operational ของช่องทางเผยแพร่ ใกล้เคียงกับ widget "แพลตฟอร์ม" (donut chart) ที่อยู่ใน sub-tab เนื้อหาอยู่แล้ว แต่คนละข้อมูล (การเชื่อมต่อ vs จำนวนคอนเทนต์) — จึงเลือกวางที่ sub-tab โซเชียลแทนเพื่อไม่ปนกับ "แพลตฟอร์ม" เดิม

## Risks / Trade-offs

- **[Risk]** ผู้ใช้ที่คุ้นเคยกับตำแหน่งเดิมของ "รออนุมัติ" (คิวรายชื่อ) และ "สถานะช่องทาง" อาจหาไม่เจอช่วงแรก → **Mitigation**: ตัวเลข "รออนุมัติ" ยังเห็นได้จากการ์ดความคืบหน้าการผลิตทันทีที่เปิดหน้า และปุ่ม "ดูทั้งหมด" เดิมที่เคยอยู่ในการ์ดรออนุมัติจะย้ายไปเป็นทางลัดจากแถบสัดส่วนแทน (ดู tasks.md)
- **[Risk]** Badge จำนวนในการ์ด "ค้างท่อนาน" ใช้ `aging.total` (รวมทุกช่วงอายุ) ซึ่งอาจตีความว่า "ต้องรีบทำทั้งหมด" ทั้งที่บางรายการเพิ่งสร้าง 1-2 วัน → **Mitigation**: ยังไม่ได้ยืนยันกับผู้ใช้ ระบุเป็น assumption ชัดเจนใน proposal.md ให้ปรับได้ภายหลัง (เปลี่ยนเป็นนับเฉพาะ 31+ วันได้ถ้าต้องการ)
- **[Risk]** การลบ widget Funnel/AI-asset-status เป็น breaking change ต่อผู้ใช้ที่อ้างอิงตัวเลขเหล่านี้ประจำ → **Mitigation**: backend ยังคำนวณและคืนค่าเดิมทุกฟิลด์ ถ้าต้องการนำกลับมาแสดงในอนาคตทำได้โดยไม่ต้องแก้ backend
