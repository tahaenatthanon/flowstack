## Context

`simplify-content-dashboard-overview` (archived 2026-09-14) เปลี่ยนแท็บภาพรวมของแดชบอร์ดคอนเทนต์เป็น 2 คอลัมน์ตามจุดประสงค์ ("ต้องดำเนินการ" ซ้าย 2/3, "ภาพรวม" ขวา 1/3) พร้อมหัวข้อกำกับ (`<h3>`) เหนือแต่ละคอลัมน์ ผู้ใช้สั่งให้ตัดหัวข้อกำกับทั้งสองออกในงานถัดมา — พอตัดออกแล้ว การสำรวจ (`/opsx:explore`) พบว่าโครง 2 คอลัมน์เดิมมีปัญหาความสูงไม่สมดุลรุนแรง ซึ่งเคยถูก "อธิบายได้" ด้วยป้ายกำกับ (สองฝั่งมีจุดประสงค์ต่างกัน ไม่จำเป็นต้องสูงเท่ากัน) แต่พอไม่มีป้ายแล้ว ความไม่สมดุลนี้ดูเหมือนเค้าโครงพังมากกว่าการจัดวางที่ตั้งใจ

วัดความสูงจริงด้วย `getBoundingClientRect()` ในเบราว์เซอร์ (จอ 1440px, ข้อมูลจริงของ tenant ปัจจุบัน):

| การ์ด | ความสูง (px) |
|---|---|
| เผยแพร่ล้มเหลว (F) | 338 |
| คอนเทนต์ที่ยังไม่เผยแพร่ (A) | 366 |
| ความคืบหน้าการผลิต (O) | 406 |
| คิวเผยแพร่ (Q) | 135 |
| กำหนดการโพสต์ถัดไป (S) | 162 |
| เนื้อหาล่าสุด (R) | 650 |

คอลัมน์ซ้าย (F+A=728) vs คอลัมน์ขวา (O+Q+S+R=1425) — ต่างกัน 697px เพราะ CSS Grid บังคับทั้งแถวสูงเท่ากับคอลัมน์ที่สูงที่สุด คอลัมน์สั้นกว่าจึงเหลือพื้นที่ว่างเปล่ายาวเท่ากับส่วนต่าง

ผู้ใช้ชี้ให้ดู `HomePage.tsx` เป็นตัวอย่าง — พบว่าใช้ pattern "หลายแถวอิสระ อัตราส่วนต่างกันต่อแถว" (`grid-cols-8` สำหรับ stat tile, `grid-cols-3 col-span-2` สำหรับคู่ detail+summary, `grid-cols-2` สำหรับคู่น้ำหนักใกล้กัน) ไม่ใช่ 2 คอลัมน์ก้อนเดียวครอบทั้งหน้า

## Goals / Non-Goals

**Goals:**
- ขจัดพื้นที่ว่างขนาดใหญ่ (~700px) ที่เกิดจากโครง 2 คอลัมน์ก้อนเดียว
- จำกัดผลกระทบของความสูงการ์ดที่ผันแปรตามข้อมูลจริง (เช่น จำนวนรายการล้มเหลว/ค้างท่อ) ให้อยู่ในขอบเขตแถวเดียว ไม่ลามทั้งหน้า
- ใช้ pattern เดียวกับ `HomePage.tsx` ที่มีอยู่แล้วในระบบ (หลายแถว อัตราส่วนต่อแถว) แทนการคิดโครงใหม่

**Non-Goals:**
- ไม่เปลี่ยน endpoint/query ฝั่ง backend
- ไม่เปลี่ยนเนื้อหา/ข้อมูลของการ์ดใดๆ (แค่จัดเรียงตำแหน่ง)
- ไม่แก้ปัญหาความสูงที่ผันแปรได้ของการ์ด "เผยแพร่ล้มเหลว" เอง (เช่น จำกัดจำนวนรายการที่แสดง + scroll ภายใน) — ระบุเป็นความเสี่ยงที่ยอมรับได้เพราะโครงหลายแถวช่วยกักผลกระทบไว้แล้ว ถ้าต้องการแก้เพิ่มควรเป็นงานแยก

## Decisions

### 1. เปลี่ยนจาก "2 คอลัมน์ก้อนเดียว" เป็น "3 แถวอิสระ อัตราส่วนต่อแถว"
**เลือก**: แบ่ง 6 การ์ดเป็น 3 คู่ แต่ละคู่อยู่คนละแถว ไม่ผูกความสูงข้ามแถว
**ทางเลือกที่พิจารณาแต่ไม่เลือก**:
- **คอลัมน์เดียว (stack ทุกการ์ดเต็มความกว้าง)**: ไม่มีทางเกิดพื้นที่ว่างอีกเลย แต่เสียการกวาดสายตา 2 คอลัมน์พร้อมกันบนจอกว้าง — ผู้ใช้ยืนยันว่ายอมรับหน้ายาวขึ้นเพื่อแลกกับการกวาดสายตา 2 คอลัมน์ จึงตัดตัวเลือกนี้ออก
- **2 คอลัมน์ก้อนเดียว แต่สลับการ์ดใหม่ให้สมดุลที่สุด** (คำนวณด้วยโปรแกรมได้ผลลัพธ์ดีที่สุดคือ `{F,O,Q,S}` vs `{A,R}` ต่างกัน 25px): ดีกว่าโครงเดิมมากแต่ยังมีความเสี่ยงเดิม — ถ้าการ์ดใดใบหนึ่งในกลุ่มสูงขึ้นผิดปกติ (เช่น "เผยแพร่ล้มเหลว" มีถึง 8 รายการ) จะดันความไม่สมดุลกลับมาทั้งคอลัมน์อีกเหมือนเดิม เพราะยังเป็นก้อนเดียวข้ามการ์ดหลายใบ
- **3 คอลัมน์เท่ากัน จัดกลุ่มตามความสูง** (ผลลัพธ์ดีที่สุด: เนื้อหาล่าสุดเดี่ยว(650) / เผยแพร่ล้มเหลว+คิว+กำหนดการ(635) / ภาพรวม+ค้างท่อ(772)): สมดุลดีมากเช่นกัน แต่เปลี่ยนสัดส่วนคอลัมน์ทั้งหน้าเป็น 3 เท่ากัน ซึ่งไม่มีที่ไหนในระบบใช้ pattern นี้ (มีแต่ 2:1 หรือ 1:1 ต่อแถว) — เลือกโครงหลายแถวแทนเพราะตรงกับ `HomePage.tsx` มากกว่าและทนทานต่อข้อมูลผันแปรกว่า (ดูเหตุผลข้อ 2)

### 2. จับคู่การ์ดต่อแถวด้วยการคำนวณละเอียดถี่ถ้วน ไม่ใช่คาดเดา
**เลือก**: คำนวณทุกวิธีจับคู่ 6 การ์ดเป็น 3 คู่ที่เป็นไปได้ (15 แบบ) ด้วยสคริปต์ เลือกชุดที่ลดผลรวมส่วนต่างความสูงต่อแถว (`sumDiff`) ต่ำที่สุด ได้ผลลัพธ์ `F+A` (28px) / `O+R` (244px) / `Q+S` (27px) รวม 299px — ดีกว่าอันดับสองที่ 379px อย่างชัดเจน
**เหตุผลที่ยังเลือกแบบนี้แม้ Row 2 ต่างกันถึง 244px**: เพราะเป็นโครง "หลายแถวอิสระ" ความไม่สมดุลของ Row 2 (เนื้อหาล่าสุด vs ความคืบหน้าการผลิต) จะไม่ลามไปกระทบ Row 1/3 เหมือนโครงเดิม — 244px ที่กักอยู่ในแถวเดียวยอมรับได้ และยังใกล้เคียงกับความไม่สมดุลที่ `HomePage.tsx` เองก็มีในแถว "ไปป์ไลน์การขาย + ซัพพอร์ต" (การ์ดรายละเอียดสูงกว่าการ์ดสรุปเป็นปกติของ pattern นี้)

### 3. Row 2 ใช้อัตราส่วน 2:1 (เนื้อหาล่าสุดกว้าง) แทน 1:1
**เลือก**: `เนื้อหาล่าสุด` (การ์ดเนื้อหาละเอียด มีรูปย่อ+หลายบรรทัดต่อรายการ) อยู่ฝั่งกว้าง (`col-span-2` ใน `grid-cols-3`), `ความคืบหน้าการผลิต` (สรุปเป็นแถบสัดส่วน กระชับ) อยู่ฝั่งแคบ
**เหตุผล**: มิเรอร์ module "รายละเอียดกว้าง + สรุปแคบ" ที่ `HomePage.tsx` ใช้ใน Row "ไปป์ไลน์การขาย + ซัพพอร์ต" และ "โปรเจกต์ล่าสุด + ใบเสนอราคา" ตรงตัว — ไม่ใช่การคิด pattern ใหม่

### 4. เปลี่ยน breakpoint จาก `xl` เป็น `lg`
**เลือก**: ทุกแถวใหม่ใช้ `lg:grid-cols-2`/`lg:grid-cols-3` (1024px) แทน `xl:grid-cols-3` (1280px) เดิม
**เหตุผล**: `HomePage.tsx` ทุกแถวใช้ `lg` เป็น breakpoint มาตรฐาน — เปลี่ยนตามให้สอดคล้องกับระบบ เนื่องจากแต่ละแถวตอนนี้มีแค่ 2 การ์ด (ไม่ใช่การ์ดรวม 4-6 ใบในคอลัมน์เดียวเหมือนเดิม) จึงไม่แออัดที่ 1024px เหมือนโครงเดิมที่จำเป็นต้องรอจอกว้างกว่า (`xl`) ถึงจะแยกคอลัมน์ได้โดยไม่บีบอัด

### 5. ขอบเขตของ "ข้อความว่างรวม" แคบลงเหลือแค่ Row 1
**เลือก**: requirement เดิม (จาก `simplify-content-dashboard-overview`) ที่ให้แสดงข้อความว่างรวมแทนการ์ด "เผยแพร่ล้มเหลว" และ "คอนเทนต์ค้างท่อ" ที่ว่างทั้งคู่ — ยังใช้ logic เดิมทุกประการ (`actionColumnEmpty`) เพียงแต่ก่อนหน้านี้มันครอบ "ทั้งคอลัมน์ซ้าย" ซึ่งบังเอิญมีแค่ 2 การ์ดนี้พอดี ตอนนี้ยังเป็น 2 การ์ดคู่เดิมใน Row 1 พอดีเช่นกัน จึงไม่ต้องเปลี่ยน logic ใดๆ แค่เปลี่ยน JSX wrapper จาก `<div className="... xl:col-span-2">` เป็น row container ใหม่

## Risks / Trade-offs

- **[Risk]** ตัวเลขความสูงที่ใช้คำนวณมาจากการวัด 1 ครั้งกับข้อมูล tenant เดียว ณ เวลาหนึ่ง — tenant อื่นหรือช่วงเวลาอื่นอาจมีสัดส่วนต่างออกไป (เช่น ไม่มีคอนเทนต์ล่าสุดเลย ทำให้ "เนื้อหาล่าสุด" สั้นลงมาก) → **Mitigation**: โครงหลายแถวเองก็ทนทานต่อกรณีนี้อยู่แล้ว เพราะการ์ดที่สั้นลงในแถวหนึ่งไม่กระทบแถวอื่น อย่างมากก็แค่ Row นั้น "สมดุลน้อยลงชั่วคราว" ไม่ใช่พังทั้งหน้า
- **[Risk]** "เผยแพร่ล้มเหลว" ไม่มีการจำกัดความสูงในตัวมันเอง (backend ส่งได้สูงสุด 8 รายการ แต่ละรายการหนา ~120-150px) หากมีรายการมากอาจทำให้ Row 1 (ปัจจุบันเกือบสมดุล 28px) เพี้ยนไปมากในบางช่วง → **Mitigation**: ยอมรับความเสี่ยงนี้ในงานนี้ (Non-Goal) เพราะผลกระทบยังคงจำกัดอยู่แค่ Row 1 เท่านั้น — ถ้าต้องการแก้ให้เสนอเป็นงานแยก (เช่น จำกัดจำนวนรายการที่แสดง + scroll ภายในการ์ด)
- **[Risk]** ลำดับการ์ดตอน stack บนจอแคบเปลี่ยนไป (เนื้อหาล่าสุดขยับขึ้นมาอยู่ตำแหน่งที่ 3 แทนตำแหน่งสุดท้าย) — ผู้ใช้ที่คุ้นกับตำแหน่งเดิมบนมือถือ/จอแคบอาจต้องปรับตัว → **Mitigation**: เป็นผลข้างเคียงที่ยอมรับได้ เพราะลำดับใหม่ยังคงเหตุผล (ล้มเหลว→ค้างท่อ→เนื้อหาล่าสุด→ภาพรวมสถานะ→คิว→กำหนดการ) และระบุไว้ชัดเจนใน proposal.md ว่าเป็นการเปลี่ยนแปลงที่มองเห็นได้ (ไม่ใช่ breaking data)

## Migration Plan

ไม่มี migration ฐานข้อมูลหรือ backend งานนี้แก้เฉพาะ JSX ใน `ContentDashboardPage.tsx` — deploy ได้ทันทีหลังผ่าน lint/build/test ปกติ, rollback ทำได้ด้วยการ revert commit เดียว
