## Context

- change `content-overview-bi-summary` (archive 25 ก.ย. 2026) ย้ายกล่องงานประจำวันเดิมลงไปใต้หัวข้อ "งานที่ต้องจัดการ" แบบคงพฤติกรรมเดิมทั้งก้อน (D7 เดิม) โดยตั้งใจเก็บไว้จนกว่าจะมีแท็บ "งานวันนี้" — แท็บนั้นยังไม่ถูกวางแผน
- ตรวจแล้ว (25 ก.ย.) ว่ากล่องในส่วนนี้ซ้ำกับส่วน BI บนหน้าเดียวกันหรือกับหน้าคอนเทนต์:

  | กล่อง | ซ้ำกับ |
  |---|---|
  | คิวเผยแพร่ | 2. Publishing Health (ตัวเลขชุดเดียวกัน) |
  | ภาพรวมสถานะคอนเทนต์ | 1. สถานะคอนเทนต์ |
  | คอนเทนต์ที่ยังไม่เผยแพร่ | 1. คอนเทนต์ที่ยังไม่เผยแพร่ (4 ช่วงอายุเดียวกัน) |
  | กำหนดการโพสต์ถัดไป / แถบเตือนเลยกำหนด | หน้าคอนเทนต์ แท็บ "กำหนดการโพสต์" (รายการรอส่ง + ป้าย "เลยกำหนด") |
  | เนื้อหาล่าสุด | หน้าคอนเทนต์ รายการคอนเทนต์ |
  | เผยแพร่ล้มเหลว | ตัวเลขอยู่ใน Publishing Health; สถานะ "ล้มเหลว" อยู่ในแท็บกำหนดการโพสต์ — **ปุ่มลองส่งใหม่และข้อความ error ไม่มีที่อื่น** |

- ผู้เรียก `?action=overview` มีเพียง `useContentOverview()` ของแท็บภาพรวม · `queue`/`aging` ใช้เฉพาะในส่วนงาน (ส่วน BI ใช้ `publishing_health` / `unpublished_aging` ที่คำนวณแยก)
- `useContentItems()` ในหน้ายังถูกส่งให้แท็บวิเคราะห์ (`items={items}`) จึงต้องคงไว้

## Goals / Non-Goals

**Goals:**
- แท็บภาพรวมเหลือเฉพาะส่วน BI 4 ส่วน ไม่มีตัวเลขซ้ำบนหน้าเดียวกัน
- ไม่เหลือโค้ด/ข้อมูล API ที่ไม่มีผู้ใช้ (NO MAGIC)

- เห็นรายการการเผยแพร่ที่ล้มเหลวพร้อมสาเหตุได้ทันทีในกล่องภาพรวมการเผยแพร่ (D4)

**Non-Goals:**
- ย้ายปุ่ม "ลองส่งใหม่" ไปที่อื่น (เช่นแท็บกำหนดการโพสต์) หรือเพิ่มลิงก์ "ดู →" จากกล่อง BI
- แท็บ "งานวันนี้"
- แก้ `api/content-publish.php` (`send_now`, `overdue_count`) — ยังมีผู้ใช้อื่น

## Decisions

### D1: ลบทั้งส่วนรวมแถบเตือนเลยกำหนด
ผู้ใช้ตัดสิน (25 ก.ย. 2026) ให้เอาออกทั้ง 6 กล่อง และยืนยันให้ลบแถบเตือนเลยกำหนดด้วย — ส่วน BI แสดงจำนวนส่งไม่สำเร็จอยู่แล้ว และแท็บกำหนดการโพสต์แสดง "เลยกำหนด"/"ล้มเหลว" ต่อรายการ
- ทางเลือกที่ไม่เลือก: เหลือแถบแจ้งเตือนเฉพาะตอนมีปัญหาในส่วน "การเผยแพร่" · ย้ายปุ่มลองส่งใหม่ไปแท็บกำหนดการโพสต์ (เปิดเป็น change แยกได้ภายหลัง)

### D2: ถอด `queue` / `aging` ออกจาก payload ด้วย
ไม่เก็บไว้ "เผื่อใช้" เพราะไม่มีผู้เรียกและทำให้ endpoint คำนวณ query เพิ่มทุกครั้ง · `publishing_health` และ `unpublished_aging` คงเดิม (คำนวณแยกอยู่แล้ว ไม่พึ่ง `queue`/`aging`) — ต้องตรวจตอนลงมือว่าไม่มีตัวแปรร่วมที่ BI ใช้ · query รายการล้มเหลวเดิมไม่ลบ แต่ย้ายไปเป็น `publishing_health.failures` (D4)
- ลบ type `StaleContentItem` เฉพาะเมื่อไม่มีผู้ใช้อื่น (ตรวจด้วย grep ก่อนลบ) · `QueueFailure` คงไว้ใช้กับ `publishing_health.failures` (ถอด `content_id`/`channel_id` ที่มีไว้สำหรับปุ่มลองส่งใหม่)

### D4: รายการที่ล้มเหลวใต้ Success Rate (ผู้ใช้ขอ 25 ก.ย. 2026)
ผู้ใช้ต้องการเห็นรายการที่มีปัญหาได้ทันทีในกล่อง "ภาพรวมการเผยแพร่" จึงเป็นข้อยกเว้นเดียวของกติกา "ส่วน BI ไม่แสดงรายการรายชิ้น"
```
┌ ภาพรวมการเผยแพร่ ─────────────────────────────┐
│ รอดำเนินการ 0 │ ส่งสำเร็จ 19 │ ส่งไม่สำเร็จ 2    │
│ Success Rate                           90.5% │
│ ─ การเผยแพร่ที่ล้มเหลว ───────────────────────── │
│ ต้นสัปดาห์เปลี่ยนงานซ้ำซาก…     [Facebook]       │
│ SEO gate: ไม่ผ่านเกณฑ์ SEO 1 ข้อ: …             │
│ ยังไม่ลองส่งใหม่ · กำหนดส่ง 2 ก.ย. 2569 12:26     │
│ …                                             │
│ แสดง 10 จาก 14 รายการ   (เมื่อเกิน)              │
└───────────────────────────────────────────────┘
```
- **ข้อมูล:** ใช้ query รายการ `failed` เดิม (JOIN `content_items` / `publish_channels`, เรียง `scheduled_at DESC`) ขยายเพดานจาก 8 เป็น 10 · จำนวนรวมใช้ `publishing_health.failed` ที่มีอยู่
- **สถานะ:** แถวในคิวที่ล้มเหลวมีสถานะ `failed` เหมือนกันทุกแถว ค่าที่มีความหมายกับผู้ดูคือการลองส่งใหม่ ("ยังไม่ลองส่งใหม่" / "ลองส่งแล้ว N ครั้ง") และวันเวลากำหนดส่ง
- **สาเหตุ:** แสดง `error_msg` เต็ม (ตัดบรรทัด) เพราะเป็นข้อมูลที่ใช้ตัดสินใจ · ว่าง → "ไม่ทราบสาเหตุ"
- **ไม่มีปุ่มลงมือทำ** ตาม D1 — ส่งใหม่จากหน้ารายละเอียดคอนเทนต์
- ทางเลือกที่ไม่เลือก: การ์ดแยกเต็มความกว้าง (ทำให้ส่วนการเผยแพร่ยาวและซ้ำกับตัวเลขในกล่อง)

### D3: ลบ state/hook ของหน้าเฉพาะที่ไม่มีผู้ใช้แล้ว
ถอด `useOverdueCount`, `useAllSchedules`, `useSendNow`, `handleRetry`, `queueStatuses`, `agingBuckets`, `statusCounts`/`workProgressStatuses`, `recentItems`, `upcomingSchedules` และ import ที่ไม่ใช้ (ยืนยันด้วย lint/tsc) — ตัว hook ใน `useContent.ts` ไม่ลบเพราะมีผู้ใช้อื่น (ตรวจก่อน) · `useContentItems` คงไว้ (แท็บวิเคราะห์ใช้)

### D5: spec ตาม UI ที่ผู้ใช้ปรับเอง
ระหว่างลงมือพบว่าผู้ใช้แก้ component ภาพรวมเอง (หลัง commit 56e0cf7): เอาหัวข้อส่วน "1.การผลิต/2.การเผยแพร่/3.ผลลัพธ์", ป้าย "ณ ตอนนี้/วันนี้–พรุ่งนี้/รายเดือน", ข้อความ "ข้อมูลทั้งหมดตั้งแต่เริ่มใช้งาน", "(อนุมัติอยู่ ณ ตอนนี้)", คำอธิบายใต้กราฟและตาราง และ "ครอบคลุม" ของกล่องเผยแพร่ออก และเปลี่ยนชื่อกล่องเป็นไทย (กระบวนการผลิตคอนเทนต์, ภาพรวมการเผยแพร่, แนวโน้มการมีส่วนร่วม, ประสิทธิภาพรายแพลตฟอร์ม) ผู้ใช้ยืนยันให้ยึด UI นี้ จึงปรับ spec (requirement ลำดับส่วน, ข้อมูลทั้งหมด, สถานะคอนเทนต์, funnel, กำหนดการ, trend) และ test ตาม และลบ `overview/shared.tsx` (`ScopeTag`/`SectionHeading`) ที่ไม่มีผู้ใช้เหลือ · ความหมายข้อมูลไม่เปลี่ยน (ขั้นอนุมัติยังนับ "อนุมัติอยู่ ณ ตอนนี้")

## Risks / Trade-offs

- [ผู้ใช้หาปุ่ม "ลองส่งใหม่" ไม่เจอ] → ส่งใหม่ได้จากหน้ารายละเอียดคอนเทนต์ ("ส่งทันที") และเห็นรายการล้มเหลวในแท็บกำหนดการโพสต์ · การนำปุ่มกลับมาที่แท็บกำหนดการโพสต์เป็นงานถัดไปที่เสนอได้
- [รายการล้มเหลวที่มี error ยาวทำให้กล่องภาพรวมการเผยแพร่สูงกว่ากล่องกำหนดการข้าง ๆ] → ยอมรับ จำกัด 10 รายการ
- [ไม่มีแจ้งเตือนเลยกำหนดบนแดชบอร์ด] → ยอมรับตามการตัดสินใจ D1
