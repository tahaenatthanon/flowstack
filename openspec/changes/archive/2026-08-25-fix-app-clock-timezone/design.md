## Context

`php.ini:1996` ตั้ง `date.timezone=Europe/Berlin` ขณะที่ MariaDB ใช้ `time_zone=SYSTEM` ซึ่งบนเครื่องนี้คือ `+07:00` และ `company_settings.timezone` ของทุก tenant (4 แถว) เป็น `Asia/Bangkok` ทั้งหมด วัดพร้อมกันได้ว่า PHP บอก `2026-08-25 04:36:48` แต่ `SELECT NOW()` บอก `2026-08-25 09:36:48` — คลาดกัน 5 ชั่วโมงโดย PHP ตามหลัง

รากเดียวกันนี้แตกออกเป็นความเสียหายสองแบบที่แยกกันชัดเจน:

**แบบที่ 1 — เขียนเวลาผิด** 20 จุดใน 12 ไฟล์เรียก `date('Y-m-d H:i:s')` แล้วเขียนลงคอลัมน์ที่ที่อื่นเขียนด้วย `NOW()` ของฐานข้อมูล จุดที่หนักที่สุดคือเส้นเผยแพร่:
- `api/content-publish.php:162` → `content_publish_queue.scheduled_at` ย้อนหลัง 5 ชั่วโมง ขณะที่ `api/cron/publish-scheduler.php:131` เขียนคอลัมน์เดียวกันด้วย `DATE_ADD(NOW(), INTERVAL 5 MINUTE)` ตอน retry → คอลัมน์เดียวมีสองนาฬิกาปนกัน และ `WHERE scheduled_at <= NOW()` ที่บรรทัด 30 ใช้นาฬิกาฐานข้อมูลตัดสิน
- `api/lib/publish-dispatch.php:516`, `api/brand-content.php:2316` และ `:2590` → ฟิลด์ `Date` ที่ POST ไปยัง Lotus Domino agent คือวันที่ที่ขึ้นบนเว็บไซต์ลูกค้า ระหว่าง 00:00–05:00 ตามเวลาไทยจะได้วันที่ของ "เมื่อวาน"

**แบบที่ 2 — อ่านเวลาผิด** (ค้นพบระหว่างสำรวจ ไม่ได้อยู่ใน proposal ตอนแรก) 7 จุดเทียบ `strtotime($ค่าจากคอลัมน์ DB)` กับ `time()` โดยตรง เพราะ `strtotime()` ตีความสตริง `'2026-08-25 09:40:01'` ด้วยเขตเวลาของ PHP (Berlin) แต่ค่านั้นถูกเขียนด้วยเวลาไทย ผลต่างจึงเป็น −300 นาทีทุกครั้ง:

| จุด | ผลที่เกิดขึ้นจริง |
|---|---|
| `api/health.php:63` | `minutes_ago: -300` — ยืนยันสด ๆ จาก `curl` แล้ว เพดาน STALE ที่ 120 นาทีจึงไม่เคยถึงจนกว่า cron จะตายเกิน 7 ชั่วโมง นี่คือเหตุผลที่ไฟดับ 15 ชั่วโมงเมื่อคืนวันที่ 24 ไม่มีอะไรเตือน |
| `api/agent-auth.php:94` | API key ที่หมดอายุแล้วยังใช้ได้อีก 5 ชั่วโมง |
| `api/billing/status.php:26` | subscription ที่หมดอายุแล้วยังเป็น `active` อีก 5 ชั่วโมง |
| `api/support-tickets.php:540` | เวลาตอบกลับครั้งแรกถูก `max(0, ...)` บีบเป็น 0 เสมอ → ตัวเลข SLA รายงานว่าตอบทันทีทุกใบ |
| `api/agent-auth.php:39` | บอกผู้เรียกให้รอ ~300 นาที ทั้งที่หน้าต่าง rate-limit สั้นกว่านั้นมาก |
| `api/lib/customer-tiering.php:99` และ `:135` | ระยะเวลาหน่วยวันคลาดไป ~0.2 วัน (คลาดจริงแต่ไม่เปลี่ยน tier) |

`api/lib/cron-runner.php:56` มีคอมเมนต์บันทึกกับดักนี้ไว้แล้ว ("`time() - strtotime(started_at)` ติดลบ ~18000 เสมอ → เพดาน 'ค้าง' ไม่เคยถึง") และแก้ด้วยการใช้ SQL ทั้งเส้น — เป็นหลักฐานว่าปัญหานี้เคยถูกเจอและถูกเลี่ยงเฉพาะจุด แทนที่จะแก้ที่ราก

JWT ไม่ได้รับผลกระทบ: `api/auth.php:29-30,57` ใช้ `time()` ทั้งฝั่งเขียนและฝั่งเทียบ ซึ่งเป็น Unix epoch ที่ไม่ขึ้นกับเขตเวลา

## Goals / Non-Goals

**Goals:**
- ทุกจุดในชั้น `api/` ตีความและเขียนเวลาบนเขตเวลาเดียวกับฐานข้อมูล โดยแก้ที่จุดเดียว
- เส้นเผยแพร่คอนเทนต์ไม่ขึ้นกับการตั้งค่า runtime เลย — ใช้นาฬิกาฐานข้อมูลเป็นแหล่งเดียว
- `api/health.php` ตรวจ cron ค้างได้จริง (ต้องเป็นบวกและต้องขึ้น `STALE` เมื่อค้างจริง)
- มีวิธีตรวจซ้ำได้ว่านาฬิกาสองฝั่งยังตรงกัน เพื่อให้เห็นทันทีถ้ามีใครย้ายเครื่องหรือแก้ `php.ini`

**Non-Goals:**
- ไม่แก้ `php.ini` เป็นทางแก้หลัก (ไม่ใช่ไฟล์ในโปรเจกต์ เครื่องใหม่จะพลาดซ้ำ)
- ไม่ย้อนแก้แถวเก่าที่เขียนเวลาผิดไปแล้ว
- ไม่เปลี่ยน `time_zone` ของ MariaDB
- ไม่ทำ multi-timezone ต่อ tenant ให้ทั้งระบบ — คงกลไก override ของ `api/capacity.php:50-60` ไว้เท่าที่มี
- ไม่แตะฝั่ง frontend และไม่แตะ 14 จุด `date()` นอกเส้นเผยแพร่ (ได้ผลถูกต้องจาก bootstrap โดยไม่ต้องแก้โค้ด)

## Decisions

### D1: ตั้งเขตเวลาที่ bootstrap `api/config.php` ไม่ใช่ที่ทุก call site
เรียก `date_default_timezone_set()` ครั้งเดียวใน `api/config.php` ตำแหน่งหลังโหลด `.env` และก่อน `define('DB_HOST', ...)`

**เหตุผล:** `api/config.php` ถูก require โดยทุก endpoint ทั้งทางตรงและผ่าน `api/auth.php:6` — ตรวจแล้วว่า `api/support-tickets.php` และ `api/billing/status.php` ที่ไม่ require `config.php` เองก็ได้ผลผ่าน `auth.php` การแก้จุดเดียวจึงซ่อมทั้งแบบที่ 1 และแบบที่ 2 พร้อมกัน เพราะ `strtotime()` จะตีความสตริงจากฐานข้อมูลเป็นเวลาไทยตรงกับที่ถูกเขียนมา

**ทางเลือกที่ตัดออก:** แก้ทั้ง 27 จุด — แตะไฟล์เยอะกว่ามาก เสี่ยงพลาดบางจุด และไม่กันจุดใหม่ที่จะเขียนในอนาคต

### D2: ค่าเขตเวลาอ่านจาก `.env` คีย์ `APP_TIMEZONE` fallback `'Asia/Bangkok'`
ตรวจความถูกต้องด้วย `new DateTimeZone()` ใน `try/catch` แล้วถอยไป `'Asia/Bangkok'` ถ้าชื่อ IANA ไม่ถูก — รูปแบบเดียวกับ `api/capacity.php:53-60` ที่พิสูจน์แล้วว่าใช้ได้

**เหตุผล:** `config.php:15-31` โหลด `.env` อยู่แล้วและใช้แบบแผน `getenv() ?: $_ENV[] ?? default` กับทุกค่า ตามแบบเดิมจึงไม่มีของใหม่ให้เรียนรู้ เครื่องที่ไม่มีคีย์นี้ได้ค่าที่ถูกอยู่แล้วจาก fallback

**ทางเลือกที่ตัดออก:** hardcode `'Asia/Bangkok'` ตรง ๆ — ใช้ได้วันนี้ แต่ทำให้ deploy ข้ามเขตเวลาต้องแก้โค้ด

### D3: ไม่อ่าน `company_settings.timezone` ที่ bootstrap
**เหตุผล:** `config.php` ทำงานก่อนที่จะมีทั้ง connection และตัวตน tenant (`requireAuth()` อยู่ใน `auth.php` ซึ่ง require `config.php`) การเปิด connection ที่ bootstrap เพื่ออ่านเขตเวลาจะกลับลำดับพึ่งพา และทำให้ทุก request มีคำสั่ง SQL เพิ่มโดยไม่จำเป็น — `api/capacity.php` ที่ต้องการเขตเวลาต่อ tenant ยัง override หลัง `requireAuth()` ได้เหมือนเดิม และจะเริ่มจากค่าเริ่มต้นที่ถูกแล้ว

### D4: เส้นเผยแพร่ใช้ `NOW()` ของ SQL เป็นแหล่งเดียว ไม่พึ่ง bootstrap
`api/content-publish.php:162` เลิกส่ง `$now` เป็น parameter แล้วเขียน `NOW()` ลงใน SQL ตรง ๆ

**เหตุผล:** D1 แก้ให้ถูกวันนี้ แต่ยังขึ้นกับการตั้งค่าที่คนเปลี่ยนได้ ส่วนเส้นนี้ยิงของออกนอกบริษัทและเรียกคืนไม่ได้ จึงควรถูกต้องโดยโครงสร้างไม่ใช่โดยการตั้งค่า และคอลัมน์ `scheduled_at` มีนาฬิกาสองตัวปนกันอยู่จริงตามที่ระบุใน Context — การรวมเป็นนาฬิกาเดียวคือการลบความกำกวมออก ไม่ใช่การเพิ่มกลไก

### D5: ฟิลด์ `Date` ที่ส่ง Domino ใช้เวลาฐานข้อมูลเป็น fallback
คงลำดับเดิมไว้ทั้งหมด — ถ้ามี `scheduled_at`/`scheduled_date`/`seo['date']` ใช้ค่านั้นก่อน (ค่าเหล่านั้นมาจากฐานข้อมูลอยู่แล้วจึงถูกต้อง) เปลี่ยนเฉพาะ fallback จาก `date('Y-m-d H:i:s')` เป็นเวลาที่อ่านจากฐานข้อมูล

`dispatch_lotusdomino()` ไม่มี `$db` ใน scope — เรียก `getDB()` ซึ่ง `api/config.php:112-124` เก็บ PDO ไว้ใน `static` จึงเป็นการใช้ connection เดิมซ้ำ ไม่ได้เปิดใหม่ และ `api/lib/publish-dispatch.php:10` ระบุไว้แล้วว่า `config.php` ถูกโหลดก่อนไฟล์นี้เสมอ

### D6: `api/health.php` แก้แยก และเปลี่ยนไปคำนวณด้วย SQL
`api/health.php` ไม่ require `config.php` เลย — โหลด `.env` เองที่บรรทัด 9-21 และสร้าง PDO เองที่บรรทัด 43-47 ดังนั้น D1 ไม่ถึงไฟล์นี้ ต้องทำสองอย่าง:
1. คำนวณอายุการรัน cron ด้วย `TIMESTAMPDIFF(MINUTE, finished_at, NOW())` ใน SQL แทน `time() - strtotime(...)` — วิธีเดียวกับที่ `api/lib/cron-runner.php` ใช้ทั้งเส้น ทำให้ผลไม่ขึ้นกับเขตเวลาของ PHP เลย
2. ตั้งเขตเวลาในไฟล์นี้ด้วย เพื่อให้ฟิลด์ `timestamp` ที่บรรทัด 96 (`date('c')`) รายงาน `+07:00` ไม่ใช่ `+02:00`

**เหตุผลที่ไม่ทำให้ `health.php` require `config.php`:** ไฟล์นี้ตั้งใจให้ยืนได้เองเพื่อจะยังตอบได้ตอนที่ config พัง ซึ่งเป็นคุณสมบัติที่ health check ควรมี — การผูกกับ bootstrap จะทำลายจุดประสงค์ของมัน

### D7: การตรวจใช้สคริปต์ CLI ตามแบบที่มีอยู่
เพิ่ม `scripts/test-app-clock-timezone.php` ตามรูปแบบของ `scripts/test-publish-dispatch-hardening.php` (กัน non-CLI, `require api/config.php`, ฟังก์ชัน `check()` นับ PASS/FAIL, exit code ไม่ศูนย์เมื่อมี FAIL)

**เหตุผล:** `pnpm test` เป็น Vitest ซึ่งทดสอบฝั่ง frontend ทดสอบนาฬิกา PHP ไม่ได้ และ repo มีแบบแผน `scripts/test-*.php` อยู่แล้ว 4 ไฟล์ — ไม่ต้องเพิ่มเครื่องมือใหม่

### D8: ไม่ย้อนแก้ข้อมูลเก่า
แถวที่เขียนเวลาผิดไปแล้วปล่อยไว้ตามเดิม

**เหตุผล:** ไม่มีทางแยกได้ว่าแถวไหนเขียนด้วย `date()` และแถวไหนเขียนด้วย `NOW()` เพราะทั้งสองลงคอลัมน์เดียวกันโดยไม่มีร่องรอยที่มา การบวก 5 ชั่วโมงทั้งคอลัมน์จะทำให้แถวที่ถูกอยู่แล้วผิด — สอดคล้องกับการตัดสินใจก่อนหน้าที่เก็บแถว `failed` 53 แถวไว้เป็นประวัติ

## Risks / Trade-offs

**[เปลี่ยนเขตเวลาแล้วโค้ดที่เคยชดเชยความคลาดไว้เองจะกลายเป็นผิด]** → `api/lib/cron-runner.php` เลี่ยงด้วยการใช้ SQL ล้วน ไม่ได้บวกลบ offset ชดเชย จึงไม่กระทบ แต่ก่อนแก้ต้อง grep หา offset ที่ hardcode ไว้ (`+ 18000`, `- 5 * 3600`, `INTERVAL 5 HOUR` และรูปแบบใกล้เคียง) เพื่อยืนยันว่าไม่มีใครชดเชยไว้เงียบ ๆ — เป็นงานข้อแรกใน tasks.md

**[ค่าที่ผู้ใช้เห็นจะกระโดด 5 ชั่วโมงทันทีหลังแก้]** → ตัวเลขอย่างเวลาตอบกลับ SLA ที่เคยเป็น 0 จะกลายเป็นค่าจริง และ `minutes_ago` ที่เคยติดลบจะเป็นบวก อาจดูเหมือนของเสียใหม่ ทั้งที่คือของที่เพิ่งเริ่มถูก → ระบุไว้ในบันทึกงานว่าคาดหวังการกระโดดนี้ และตรวจ `api/health.php` ก่อน/หลังเทียบกันเป็นหลักฐาน

**[API key และ subscription ที่หมดอายุจะถูกตัดสิทธิ์เร็วขึ้น 5 ชั่วโมงทันที]** → เป็นพฤติกรรมที่ถูกต้อง แต่ถ้ามีคีย์ที่หมดอายุอยู่ในช่วง 5 ชั่วโมงนั้นพอดี ผู้ใช้จะถูกตัดกลางทาง → ตรวจ `agent_api_keys` และตาราง subscription ว่ามีแถวที่ `expires_at` อยู่ในกรอบ 5 ชั่วโมงข้างหน้าหรือไม่ก่อนแก้ ถ้ามีให้แจ้งเจ้าของระบบ ไม่ใช่เลื่อนวันหมดอายุให้เอง

**[`api/health.php` ยังคงมีตรรกะ `.env` และ PDO ซ้ำกับ `config.php`]** → ยอมรับความซ้ำนี้ตาม D6 เพราะเป็นราคาของการที่ health check ยืนได้เองเมื่อ config พัง — ไม่รวมเข้าด้วยกันใน change นี้

**[`.env` มีคีย์ใหม่ที่ไม่ได้อยู่ใน version control]** → `.env` ถูก gitignore ที่ `.gitignore:6` เครื่องอื่นที่ไม่มี `APP_TIMEZONE` จะได้ `'Asia/Bangkok'` จาก fallback ซึ่งถูกต้องสำหรับทุก tenant ปัจจุบัน จึงไม่พังแบบเงียบ
